# deployment-operations Specification

## Purpose
Описывает развёртывание и эксплуатацию Tasklerq: конфигурацию, PostgreSQL,
Docker, Telegram webhook, health, фоновые задания, обновления, резервное
копирование и локальную разработку.

## Requirements

### Requirement: Конфигурация через окружение

Система SHALL читать конфигурацию из переменных окружения и MUST завершать
запуск с понятной ошибкой, если отсутствует обязательный параметр или он
невалиден. Обязательные параметры MUST включать `DATABASE_URL`; `ENV` MUST
быть необязательным со значением по умолчанию `production`; при
`TELEGRAM_MODE=webhook` или `polling` в окружении — `TELEGRAM_BOT_TOKEN`, а для
webhook также `TELEGRAM_WEBHOOK_SECRET` и адрес webhook; при явно заданном в
окружении `LLM_CAPTURE_ENABLED=true` — адрес и модель основного слота
(`LLM_PRIMARY_URL`, `LLM_PRIMARY_MODEL`). Настройки Telegram MUST браться из
окружения целиком, только если задан `TELEGRAM_BOT_TOKEN`; иначе — из консоли
оператора, а без них Telegram MUST быть выключен; прочие переменные `TELEGRAM_*`
без токена MUST игнорироваться с предупреждением. `PUBLIC_BASE_URL` MUST быть
необязательным; если он задан, в production он MUST быть HTTPS-URL. Параметры
LLM, не заданные окружением, MAY браться из настроек консоли оператора; значение
из окружения MUST иметь приоритет. Слот MUST считаться заданным окружением,
только если задан его адрес или модель; прочие переменные слота без них MUST
игнорироваться с предупреждением без значений. Резервный слот MUST считаться
настроенным, только если заданы и его адрес, и его модель; заданный наполовину
MUST приводить к ошибке запуска. Переменные `HA_BASE_URL`, `HA_TOKEN` и
`HA_AI_TASK_ENTITY_ID` больше не читаются; если они заданы, сервис MUST
запуститься и MUST записать предупреждение без их значений. Необязательные
`ADMIN_BIND_ADDR` (адрес консоли или `disabled`), `ADMIN_TRUSTED_PROXIES`
(список сетей CIDR) и `TASKLERQ_SECRET_KEY` (32 байта в base64) MUST
проверяться при запуске.

#### Scenario: Отсутствует DATABASE_URL

- **WHEN** сервис запускается без `DATABASE_URL`
- **THEN** процесс завершается с кодом ошибки
- **AND** сообщение указывает отсутствующий параметр
- **AND** секреты не выводятся

#### Scenario: Невалидный URL

- **WHEN** `PUBLIC_BASE_URL` задан и не является HTTPS-URL в production
- **THEN** сервис отказывается запускаться
- **AND** сообщает ожидаемый формат

#### Scenario: Запуск без PUBLIC_BASE_URL

- **WHEN** сервис запускается только с `DATABASE_URL` и
  `TELEGRAM_MODE=disabled`
- **THEN** сервис стартует в окружении `production`
- **AND** консоль оператора доступна на адресе по умолчанию
- **AND** настройки LLM в консоли можно изменять

#### Scenario: Запуск только с DATABASE_URL

- **WHEN** сервис запускается только с `DATABASE_URL`, а в консоли Telegram не
  настроен
- **THEN** сервис стартует с выключенным Telegram
- **AND** HTTP API и консоль работают

#### Scenario: Режим Telegram без токена

- **WHEN** в окружении задан `TELEGRAM_MODE=disabled` без `TELEGRAM_BOT_TOKEN`
- **THEN** сервис стартует, а настройки Telegram берутся из консоли
- **AND** лог содержит предупреждение, что `TELEGRAM_MODE` без токена
  игнорируется

#### Scenario: Webhook без токена

- **WHEN** в окружении задан `TELEGRAM_MODE=webhook` без `TELEGRAM_BOT_TOKEN`
- **THEN** сервис отказывается запускаться и называет `TELEGRAM_BOT_TOKEN`

#### Scenario: LLM включён без основного слота

- **WHEN** `LLM_CAPTURE_ENABLED=true`, а `LLM_PRIMARY_URL` не задан
- **THEN** процесс завершается с кодом ошибки
- **AND** сообщение называет отсутствующий параметр

#### Scenario: Таймаут слота без адреса

- **WHEN** в окружении задан только `LLM_PRIMARY_TIMEOUT_MS=10000`
- **THEN** сервис стартует
- **AND** лог содержит предупреждение, что переменная игнорируется
- **AND** основной слот можно задать в консоли

#### Scenario: Резервный слот задан наполовину

- **WHEN** задан `LLM_FALLBACK_URL`, а `LLM_FALLBACK_MODEL` пуст
- **THEN** сервис отказывается запускаться и называет недостающий параметр

#### Scenario: Остались переменные Home Assistant

- **WHEN** в окружении заданы `HA_TOKEN` и корректные параметры основного слота
- **THEN** сервис запускается
- **AND** лог содержит предупреждение, что `HA_TOKEN` не используется, без его
  значения

#### Scenario: Невалидный ключ шифрования

- **WHEN** `TASKLERQ_SECRET_KEY` задан, но не декодируется в 32 байта
- **THEN** сервис отказывается запускаться
- **AND** сообщение называет параметр и ожидаемый формат без значения

### Requirement: Секреты и безопасные значения по умолчанию

Секреты MUST NOT храниться в репозитории и MUST NOT выводиться в лог при старте;
единственное исключение — setup-код консоли, который выводится, пока учётной
записи администратора нет и консоль включена. Значения по умолчанию MUST быть
безопасными: сервис не должен запускаться в production без webhook-секрета,
если Telegram включён.

#### Scenario: Секреты не логируются

- **WHEN** сервис стартует с корректной конфигурацией и существующей учётной
  записью администратора
- **THEN** лог содержит имена параметров и версию
- **AND** не содержит значений токенов, паролей и setup-кода

#### Scenario: Консоль выключена

- **WHEN** сервис стартует с `ADMIN_BIND_ADDR=disabled` без учётной записи
  администратора
- **THEN** setup-код не выпускается и в лог не выводится

### Requirement: Режим без Telegram и параметры capture

Режим `TELEGRAM_MODE=disabled` MUST позволять запуск без Telegram и без
`TELEGRAM_BOT_TOKEN`. Параметры внешнего capture MUST включать
`CAPTURE_API_ENABLED`, `CAPTURE_VOICE_TIMEOUT_MS`, `CAPTURE_VOICE_FALLBACK_RAW`,
`CAPTURE_RATE_LIMIT_PER_MIN` и `CAPTURE_MAX_TEXT_CHARS`.

#### Scenario: Headless-режим без Telegram

- **WHEN** сервис запускается с `TELEGRAM_MODE=disabled` без
  `TELEGRAM_BOT_TOKEN`
- **THEN** сервис стартует
- **AND** HTTP API и внешний capture работают
- **AND** webhook и исходящие сообщения отключены

#### Scenario: Capture отключён

- **WHEN** `CAPTURE_API_ENABLED=false`
- **THEN** эндпоинты capture возвращают `503`
- **AND** остальные API продолжают работать

### Requirement: Режим размещения и первый владелец в конфигурации

Режим размещения MUST задаваться `TENANCY_MODE` со значениями `single` (по
умолчанию) и `multi`. Необязательный `BOOTSTRAP_OWNER_TELEGRAM_ID` MUST быть
положительным целым; если он не задан, Telegram включён и учётки администратора
консоли нет, при старте MUST выводиться предупреждение, что первым владельцем
станет первый написавший боту.

#### Scenario: Режим размещения по умолчанию

- **WHEN** сервис запускается без `TENANCY_MODE`
- **THEN** используется режим `single`

#### Scenario: Невалидный режим размещения

- **WHEN** `TENANCY_MODE=saas`
- **THEN** сервис отказывается запускаться
- **AND** сообщение перечисляет допустимые значения `single` и `multi`

#### Scenario: Невалидный Telegram ID первого владельца

- **WHEN** `BOOTSTRAP_OWNER_TELEGRAM_ID=abc`
- **THEN** сервис отказывается запускаться
- **AND** сообщение указывает параметр и ожидаемый формат

#### Scenario: Первый владелец не ограничен

- **WHEN** Telegram включён, `BOOTSTRAP_OWNER_TELEGRAM_ID` не задан и учётки
  администратора нет
- **THEN** сервис стартует
- **AND** лог содержит предупреждение о том, что первым владельцем станет первый
  написавший боту

#### Scenario: Учётка администратора есть

- **WHEN** Telegram включён, `BOOTSTRAP_OWNER_TELEGRAM_ID` не задан, а учётка
  администратора создана
- **THEN** предупреждение о первом написавшем не выводится

### Requirement: PostgreSQL

Система SHALL использовать PostgreSQL версии 15 или новее как единственное
хранилище данных. Подключение MUST осуществляться через пул соединений
размером от 5 до 20; `statement_timeout` MUST быть ограничен. Миграции MUST
применяться при старте под advisory lock или отдельной командой и MUST быть
совместимы с предыдущей версией приложения на время обновления. При
недоступности базы readiness MUST возвращать ошибку, а сервис MUST NOT
принимать пользовательские запросы.

#### Scenario: Применение миграций

- **WHEN** сервис запускается на пустой базе
- **THEN** миграции применяются по порядку
- **AND** повторный запуск не применяет их повторно

#### Scenario: Ошибка миграции

- **WHEN** миграция завершается ошибкой
- **THEN** сервис не запускается в рабочий режим
- **AND** в логе указана миграция и причина
- **AND** данные не остаются в частично изменённом состоянии

#### Scenario: База недоступна

- **WHEN** PostgreSQL недоступен
- **THEN** `/health/ready` возвращает ошибку
- **AND** webhook не подтверждает обработку обновлений

### Requirement: Docker-развёртывание

Система SHALL поставляться в виде Docker-образа, запускаемого от непривилегированного
пользователя. Образ MUST содержать healthcheck, MUST поддерживать graceful
shutdown и MUST не требовать записи в корневую файловую систему. Пример
Docker Compose MUST описывать сервис Tasklerq, внешнюю сеть для PostgreSQL и
Home Assistant, публикацию порта только на loopback и ограничение ресурсов.
Секреты MUST передаваться через env-file с ограниченными правами или Docker
secrets.

#### Scenario: Запуск контейнера

- **WHEN** контейнер запускается с корректным env-file
- **THEN** сервис становится healthy
- **AND** порт доступен только через reverse proxy

#### Scenario: Graceful shutdown

- **WHEN** контейнер получает `SIGTERM`
- **THEN** сервис перестаёт принимать новые задания
- **AND** завершает текущие операции в течение 30 секунд
- **AND** очередь не теряет обновления

#### Scenario: Read-only filesystem

- **WHEN** контейнер запущен с `read_only: true`
- **THEN** сервис работает, используя tmpfs для временных файлов
- **AND** не пытается писать в корень образа

### Requirement: Telegram webhook и TLS

Система SHALL принимать webhook по HTTPS-адресу и пути `/webhooks/telegram`.
Адрес webhook MUST браться из `TELEGRAM_WEBHOOK_URL` или из настройки консоли, а
без них — из публичного адреса с этим путём. Запрос MUST проверять заголовок
`X-Telegram-Bot-Api-Secret-Token` сравнением с секретом за постоянное время;
несовпадение MUST возвращать `401` без деталей. Размер тела MUST быть ограничен
1 МБ. Система MUST регистрировать webhook при старте и при сохранении настроек
Telegram в консоли и MUST логировать результат без токена.

#### Scenario: Регистрация webhook

- **WHEN** сервис стартует с `TELEGRAM_WEBHOOK_URL`
- **THEN** он вызывает `setWebhook` с секретом и списком допустимых обновлений
- **AND** логирует успешный результат

#### Scenario: Неверный секрет

- **WHEN** запрос приходит без корректного секрета
- **THEN** сервис возвращает `401`
- **AND** обновление не сохраняется

#### Scenario: Регистрация из консоли

- **WHEN** администратор сохраняет в консоли публичный адрес
  `https://tasklerq.example.com` без переопределения адреса webhook
- **THEN** `setWebhook` вызывается с адресом
  `https://tasklerq.example.com/webhooks/telegram`
- **AND** перезапуск процесса не нужен

### Requirement: Polling только вне production

В production режим polling MUST быть запрещён; polling может использоваться
только в development.

#### Scenario: Polling в production

- **WHEN** `TELEGRAM_MODE=polling` при `ENV=production`
- **THEN** сервис отказывается запускаться
- **AND** сообщает использовать webhook

### Requirement: Health и наблюдаемость

Система SHALL предоставлять `/health/live` для проверки процесса и
`/health/ready` для проверки базы, применённых миграций и допустимой задержки
очередей. Если в режиме `single` активных household больше одного,
`/health/ready` MUST оставаться успешным и MUST содержать предупреждение о
деградации без названий и идентификаторов household. При включённом LLM
`/health/ready` MUST оставаться успешным независимо от состояния слотов и MUST
содержать предупреждение, если предохранители всех настроенных слотов
разомкнуты или если какой-либо слот не имеет статуса проверки «прошёл». Если в
базе есть зашифрованные настройки, а ключ шифрования не задан или не подходит,
`/health/ready` MUST оставаться успешным и MUST содержать предупреждение
`secret_key_missing` или `secret_undecryptable`.

#### Scenario: Успешная readiness

- **WHEN** база доступна, миграции применены, очередь не переполнена
- **THEN** `/health/ready` возвращает `200`
- **AND** содержит версию и время проверки

#### Scenario: Переполненная очередь

- **WHEN** задержка очереди превышает настроенный порог
- **THEN** `/health/ready` возвращает ошибку
- **AND** метрика задержки отражает значение

#### Scenario: Readiness в деградированном режиме

- **WHEN** в режиме `single` в базе два активных household, а остальные
  проверки пройдены
- **THEN** `/health/ready` возвращает `200`
- **AND** ответ содержит предупреждение `multiple_households`

#### Scenario: Все слоты LLM недоступны

- **WHEN** предохранители основного и резервного слотов разомкнуты, а
  остальные проверки пройдены
- **THEN** `/health/ready` возвращает `200`
- **AND** ответ содержит предупреждение `llm_unavailable`

#### Scenario: Слот не проверен

- **WHEN** основной слот не проходил проверку smoke-набором
- **THEN** `/health/ready` возвращает `200`
- **AND** ответ содержит предупреждение `llm_slot_unverified` с именем слота

#### Scenario: Секреты без ключа

- **WHEN** в базе сохранён токен слота, а сервис запущен без
  `TASKLERQ_SECRET_KEY`
- **THEN** `/health/ready` возвращает `200`
- **AND** ответ содержит предупреждение `secret_key_missing`

#### Scenario: Слот появился в консоли

- **WHEN** сервис запущен без слотов, а затем основной слот задан в консоли и
  не проверялся
- **THEN** `/health/ready` без перезапуска содержит предупреждение
  `llm_slot_unverified` с именем слота

### Requirement: Структурированные логи и метрики

Логи MUST быть структурированными JSON и MUST содержать `request_id`,
`update_id` (для webhook), длительность и результат операции. Логи MUST NOT
содержать текст сообщений, токены и персональные данные. Система MUST
предоставлять метрики количества обновлений, ошибок, задержки очередей, LLM и
доставки; метрики MUST быть защищены от публичного доступа.

#### Scenario: Логи без PII

- **WHEN** пользователь отправляет задачу с названием «Купить лекарство»
- **THEN** лог содержит идентификатор обновления и результат
- **AND** не содержит название задачи

### Requirement: Фоновые задания

Система SHALL выполнять обработку Telegram-обновлений, отправку outbox,
напоминания и очистку данных через фоновые воркеры в том же процессе. Задания
MUST захватываться через `FOR UPDATE SKIP LOCKED` или эквивалентный механизм,
безопасный для нескольких экземпляров. Воркеры MUST поддерживать retry с
экспоненциальной задержкой и MUST корректно завершаться при остановке.
Повторная обработка задания MUST быть идемпотентной.

#### Scenario: Падение воркера

- **WHEN** воркер завершается во время обработки обновления
- **THEN** задание возвращается в очередь после истечения блокировки
- **AND** обрабатывается другим воркером
- **AND** эффект применяется один раз

#### Scenario: Остановка сервиса

- **WHEN** сервис получает сигнал остановки
- **THEN** воркеры завершают текущие задания
- **AND** незавершённые задания остаются в очереди

#### Scenario: Несколько экземпляров

- **WHEN** запущены два экземпляра сервиса
- **THEN** каждое задание обрабатывается только одним экземпляром
- **AND** дубликаты не возникают

### Requirement: Обновления и откат

Система SHALL публиковать версионированные Docker-образы с тегом semver и
git SHA. Миграции MUST следовать схеме expand/contract: сначала добавляются
совместимые изменения, затем удаляются устаревшие в следующем релизе. Откат
MUST быть возможен на предыдущий образ без потери данных. Перед обновлением
MUST создаваться резервная копия базы. Разрушительные миграции MUST NOT
выполняться в том же релизе, что и код, который перестаёт использовать старые
поля.

#### Scenario: Обновление

- **WHEN** развёртывается новая версия
- **THEN** миграции применяются до запуска нового кода
- **AND** сервис проходит readiness
- **AND** старые данные остаются доступными

#### Scenario: Откат

- **WHEN** новая версия не проходит проверку
- **THEN** развёртывается предыдущий образ
- **AND** схема остаётся совместимой
- **AND** данные не теряются

#### Scenario: Разрушительная миграция

- **WHEN** релиз содержит удаление колонки, используемой предыдущей версией
- **THEN** релиз отклоняется на этапе проверки
- **AND** удаление переносится в следующий релиз

### Requirement: Резервное копирование и retention

Система SHALL документировать и поддерживать ежедневное резервное копирование
PostgreSQL с хранением не менее 14 дней и выносом копии за пределы хоста.
Восстановление MUST быть проверено не реже одного раза в квартал. Система MUST
удалять `telegram_updates` через 7 дней, черновики capture через 30 дней,
`llm_runs` через 90 дней, события задач через 365 дней, мягко удалённые задачи
через 30 дней и отправленный outbox через 30 дней. Сроки MUST быть
конфигурируемыми.

#### Scenario: Ежедневная копия

- **WHEN** наступает время backup
- **THEN** создаётся дамп базы
- **AND** копия сохраняется вне хоста
- **AND** ошибка backup увеличивает метрику

#### Scenario: Восстановление

- **WHEN** база потеряна
- **THEN** последний дамп восстанавливается в новую базу
- **AND** сервис проходит readiness
- **AND** данные задач и household доступны

#### Scenario: Очистка старых данных

- **WHEN** фоновое задание retention запускается
- **THEN** удаляются записи старше настроенных сроков
- **AND** активные задачи и household не затрагиваются

### Requirement: Локальная разработка

Система SHALL предоставлять локальную конфигурацию Docker Compose с
PostgreSQL и возможностью запуска Telegram в режиме polling. Для разработки
MUST быть доступны подмена Telegram API и Home Assistant через локальные
mock-серверы, seed-данные и интеграционные тесты. Запуск MUST не требовать
публичного домена и production-секретов.

#### Scenario: Локальный запуск

- **WHEN** разработчик запускает `docker compose up` в dev-режиме
- **THEN** поднимается PostgreSQL и сервис
- **AND** бот работает через polling с тестовым токеном

#### Scenario: Моки внешних систем

- **WHEN** запускаются интеграционные тесты
- **THEN** Telegram и Home Assistant заменены mock-серверами
- **AND** тесты не обращаются в интернет

### Requirement: Административный CLI

Система SHALL предоставлять CLI `tasklerq admin` для создания и отзыва
API-токенов, просмотра статистики очередей, проверки webhook, списка household,
создания и удаления household и добавления пользователя по Telegram ID с ролью
`owner` или `member` (для режима без онбординга в боте), а также для выпуска
setup-кода консоли, сброса пароля администратора и ротации ключа шифрования.
Команды MUST работать с той же конфигурацией, что и сервис, включая настройки
консоли. Вывод MUST NOT содержать секреты и полные токены; новый токен,
setup-код и ссылка восстановления показываются один раз.

#### Scenario: Создание токена

- **WHEN** администратор выполняет `tasklerq admin token create --name "Home Assistant" --scopes ha:read,ha:write`
- **THEN** CLI выводит токен один раз
- **AND** в базе сохраняется только хеш
- **AND** повторный вывод невозможен

#### Scenario: Статистика очередей

- **WHEN** администратор выполняет `tasklerq admin queue stats`
- **THEN** CLI показывает количество ожидающих, обрабатываемых и ошибочных
  заданий
- **AND** не показывает содержимое сообщений

#### Scenario: Ротация ключа шифрования

- **WHEN** администратор выполняет `tasklerq admin secret-key rotate` с прежним
  ключом в `TASKLERQ_SECRET_KEY_OLD` и новым в `TASKLERQ_SECRET_KEY`
- **THEN** каждый секрет, зашифрованный прежним ключом, перешифрован новым в
  одной транзакции
- **AND** если хоть один секрет не расшифровывается ни одним из ключей, ничего не
  меняется и команда называет имя настройки

#### Scenario: Ротация при работающем сервисе

- **WHEN** сервис работает с `TASKLERQ_SECRET_KEY_OLD` и новым
  `TASKLERQ_SECRET_KEY`, а ротация ещё не выполнена
- **THEN** сервис расшифровывает секреты обоими ключами
- **AND** новые и изменённые секреты шифрует новым ключом

### Requirement: Создание и удаление household через CLI

Создание household MUST позволять сразу указать владельца по Telegram ID;
household и владелец создаются атомарно. В режиме `single` создание household
MUST отклоняться, если активный household уже есть. Удаление household через CLI
MUST быть мягким и MUST отзывать токены и приглашения так же, как удаление
владельцем.

#### Scenario: Household без Telegram

- **WHEN** администратор выполняет
  `tasklerq admin household create --name "Семья" --timezone Europe/Moscow` на
  пустой инсталляции
- **THEN** создаются household и списки «Задачи», «Покупки» и «Календарь»
- **AND** CLI выводит идентификатор household для создания токенов
- **AND** CLI выводит подсказку, как добавить владельца командой `admin user add`

#### Scenario: Household с владельцем одной командой

- **WHEN** администратор выполняет
  `tasklerq admin household create --name "Семья" --owner-telegram-id 123456789 --owner-name "Алексей"`
  на пустой инсталляции
- **THEN** в одной транзакции создаются household, три списка и владелец с этим
  Telegram ID
- **AND** при первом обращении к боту владелец видит главное меню без онбординга

#### Scenario: Второй household в режиме single

- **WHEN** в режиме `single` активный household уже есть и администратор
  выполняет `tasklerq admin household create`
- **THEN** команда завершается ошибкой `409`
- **AND** ничего не меняется

#### Scenario: Список household

- **WHEN** администратор выполняет `tasklerq admin household list`
- **THEN** CLI показывает для каждого активного household идентификатор,
  название, часовой пояс, Telegram ID владельца (или его отсутствие), число
  участников, число открытых задач и число активных токенов
- **AND** не показывает содержимое задач и токены

#### Scenario: Удаление household

- **WHEN** администратор выполняет
  `tasklerq admin household delete --household <id> --yes`
- **THEN** household и его участники помечаются удалёнными
- **AND** токены и приглашения household отзываются
- **AND** в аудите есть событие удаления с системным актором

### Requirement: Выбор household и добавление пользователя в CLI

Токены и пользователи принадлежат household: в режиме `single` `--household` MAY
опускаться, если household единственный; в режиме `multi` `--household` MUST
быть указан явно. Добавление пользователя MUST записывать событие
`member_joined`, отклонять Telegram ID, уже состоящий в другом household, и
второго `owner`.

#### Scenario: Режим multi без household

- **WHEN** в режиме `multi` администратор выполняет `tasklerq admin token create`
  без `--household`
- **THEN** команда завершается ошибкой с требованием указать `--household`
- **AND** ничего не меняется

#### Scenario: Добавление владельца по Telegram ID

- **WHEN** администратор выполняет
  `tasklerq admin user add --telegram-id 123456789 --role owner --name "Алексей"`
- **THEN** в единственном household появляется владелец с этим Telegram ID
- **AND** в журнале членства есть событие `member_joined` с источником CLI

#### Scenario: Telegram ID уже занят

- **WHEN** администратор добавляет Telegram ID, который состоит в другом household
- **THEN** CLI завершается ошибкой и ничего не меняет

### Requirement: Подтверждение опасных команд CLI

Опасные команды (отзыв токена, удаление household) MUST требовать явного
подтверждения.

#### Scenario: Удаление без подтверждения

- **WHEN** администратор выполняет `tasklerq admin household delete --household <id>`
  без `--yes`
- **THEN** CLI запрашивает подтверждение
- **AND** без подтверждения ничего не меняет

#### Scenario: Опасная команда

- **WHEN** администратор пытается отозвать токен без флага подтверждения
- **THEN** CLI запрашивает подтверждение
- **AND** без подтверждения ничего не меняет

### Requirement: Запуск на схеме с более новыми миграциями

Сервис SHALL запускаться и проходить readiness на базе, где кроме всех
встроенных в образ миграций применены и миграции, которых в образе нет.
Такие миграции MUST NOT считаться ошибкой запуска. Сервис MUST перечислять
их версии в предупреждении в логе при старте.

#### Scenario: Откат на предыдущий образ после аддитивной миграции

- **WHEN** новая версия применила аддитивную миграцию, а затем развёрнут
  предыдущий образ, в котором этой миграции нет, но есть это требование
- **THEN** предыдущий образ запускается и проходит `/health/ready`
- **AND** в логе при старте есть предупреждение с версией неизвестной миграции
- **AND** данные, записанные новой версией, остаются в базе
