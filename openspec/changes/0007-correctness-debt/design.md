# Design

## Context

Мотивация и список — в proposal.md, поведение — в дельтах спек. Ниже
способ исправления там, где он не очевиден, и пункты из PR, которые при
проверке оказались не дефектами.

## Goals / Non-Goals

**Goals:**

- Каждый пункт закрыт тестом, который падает на текущем `main`.
- Без миграций и без изменений HTTP API.

**Non-Goals.** Пункты из PR, которые при проверке оказались не дефектами:

- **Гонка дублей при прямом добавлении (PR 18).** Воркер разбора и воркер
  обновлений одиночные и обрабатывают задания последовательно
  (`telegram/runtime.rs:111-132`). Два «молоко» всегда идут по очереди.
  Остаётся миллисекундное окно между воркером разбора и сохранением в
  редакторе, худший исход — две позиции «Молоко».
- **Предел суммы дубликатов 9999 (PR 18).** Нужно, чтобы LLM вернул две
  одинаковые позиции примерно по 9000. Исправление добавило бы конфликт
  устаревшей версии у второго выбора.
- **Предел повторов сохранения редактора (PR 16).** Каждый повтор требует
  чужого коммита между чтением и записью. На практике цикл конечен.
- **Half-open предохранитель (PR 2).** Параллельных вызовов LLM после паузы
  максимум два-три: последовательный воркер и голосовой HTTP-capture. Цена
  — лишний неудачный вызов.
- **Граница retention для `Idempotency-Key` (PR 2).** Окно — секунды
  задержки LLM у границы в 30 дней. Нужен повтор ключа месячной давности.
- **Запись `llm_runs` при сбое пула (PR 2).** Если база недоступна, записать
  некуда. Недосчёт квоты — единицы.
- **Отметка ошибки доставки (PR 5).** Строка outbox уже получает `dead`,
  `dead_at`, `last_error` и метрику `outbox_dead`. Доставка ссылается на неё
  через `outbox_seq`. Повторного планирования нет: `insert_with_flags`
  проверяет `pending`/`sent`.
- **Snooze блока сводного после retention (PR 20).** Нужно листать сводное
  сообщение старше 30 дней (`RETENTION_OUTBOX_DAYS`), исход косметический.
- **Ограничение `CHECK` на `origin_key` (0005, Migration Plan п.4).** Старые
  `sent`/`cancelled` snooze без привязки обновляет `ON DELETE SET NULL` по
  `outbox_seq` при очистке outbox и `set_batch_state` в блоках. Ограничение
  `NOT VALID` сломало бы retention. Хватает правки в коде (решение 4).
- **Лимитер для удаления якоря (PR 7).** Следующая отправка сама получает
  `429` и ставит общую паузу (`outbox.rs:546-562`), строка не теряется.
- **Toast повторного callback (PR 9).** Экран обновляется. В уведомлениях
  результат виден в самом сообщении. На карточке «✓ Выполнено» и так
  показывает баннер.
- **Версия списков и `deleted_list_ids` (PR 3).** `tasklerq-ha` списки не
  меняет: в `api.py` для списков только `POST /lists/{id}/items`. Snapshot
  всегда отдаёт полный массив списков. «Last write wins» для списков
  записано в `docs/ha-api.md` §1.5 и §8.
- **Ключ /64 для `auth_failed` (PR 6).** Поток событий аудита по типу уже
  ограничен `MAX_RECORDS_PER_WINDOW = 50` (`security_audit.rs:35`).
- **Конец тихих часов на переходе DST (PR 5).** Уже работает через
  `resolve_local()`. Тест на это добавляет 0008.
- **Длина цитаты в карточке черновика (PR 7).** Уже ограничена
  `card_quotes()`.
- Snooze при смене исполнителя, догон пропущенной сводки, «Без срока» в
  редакторе повторяющейся задачи — нужны продуктовые решения, не входят.

## Decisions

### 1. Баннер над меню, если экран не собирается

`present_to()` (`bot/mod.rs`) при `Fail::User` один раз повторяет показ с
`Screen::Menu` и тем же баннером. Если не удалось показать и меню, ошибка
пишется в лог и задание не роняет.

### 2. Отмена прямого добавления

- `Action::AddedUndo` получает `#[serde(default)] draft_id: Option<Uuid>`.
  Старые токены разбираются с `None`.
- `present_after_undo()` вызывает готовую `present_after_duplicate()`
  (`shopping.rs:387`). Та уже показывает список, только если текущий экран
  — этот список, иначе текущий экран.
- В действия выбора дубликата добавляются идентификаторы позиций,
  созданных исходным добавлением (`#[serde(default)]`, рядом с `rest` и
  `draft_id`). Следующий баннер строит из них «↩️ Отменить».
  `addition_rows()` принимает `&[Item]`. Позиции загружаются по
  идентификаторам, или сигнатура меняется на идентификаторы, если на кнопку
  хватает их одних.

### 3. «Без срока» у задачи без срока

В `set_due` (`card.rs`) ветка, где нет ни `due_at`, ни `due_date`, сразу
показывает карточку без баннера и без вызова `items::update`. Пустой патч и
сейчас ничего не пишет, поэтому версия не растёт и дальше.

### 4. Snooze без привязки — устаревший

В `reminder_stale()` (`jobs/notice.rs:204`):

```rust
return self.origin_key.as_deref()
    != Some(snooze_origin(self.item_due_at, self.item_due_date).as_str());
```

Существующий `cancel_stale` для напоминаний охватывает snooze и отменит
оставшиеся pending без привязки на ближайшем тике. `deliver_one` перед
отправкой тоже проверяет актуальность.

Такие записи могли появиться только до 0014: создавать их перестали с
сегодняшнего деплоя, а живут они не дольше ~33 часов. Если 0007 выкатить
раньше этого окна, пропадёт максимум один snooze, отложенный до деплоя
0005. Это допустимо.

### 5. Независимые шаги тика

`Scheduler::tick()` выполняет каждый шаг отдельно. Ошибка шага пишется
`tracing::error!(step = "...", %error)`, и выполнение переходит к следующему
шагу. Если упал хотя бы один шаг, `tick()` возвращает `Err` последней ошибки,
иначе `Ok(stats)`. Поэтому 160 мест вызова в тестах и цикл планировщика не
меняются.

Независимость шагов безопасна по двум причинам:
- `deliver_one` перед отправкой снова вызывает `cancel_if_stale`
  (`delivery.rs:280`), поэтому доставка без предшествующей отмены
  устаревших не отправит лишнего;
- перенос на тихие часы проверяется под блокировкой
  (`postpone_for_quiet`).

Тест: в тестовой базе триггер `BEFORE INSERT ON notification_deliveries
WHEN (NEW.kind = 'digest')` бросает исключение. Тик всё равно доставляет
напоминание, а в логе есть ошибка с названием шага.

### 6. Текст без печатаемых символов

В обработчике внешнего capture длина проверяется по
`sanitize(text).trim()`. Это та же `sanitize()`, что уже используется для
fallback-названия. Пустой результат даёт `422` до квоты и до LLM.

## Risks / Trade-offs

- [Повтор показа с меню скрывает баг в сборке экрана] → `Fail::User` и
  сейчас пишется в лог, повтор добавляет только показ результата.
- [Решение 4 отменяет pending snooze без привязки, если деплой случился в
  первые ~33 часа после 0005] → потеря не больше одного snooze, отложенного
  до деплоя 0005.
