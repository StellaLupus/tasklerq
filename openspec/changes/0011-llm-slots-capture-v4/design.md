# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что определяет подход.

- Все пути разбора (Telegram-воркер, внешний capture, `capture-eval`) вызывают
  LLM через один шов: `capture::llm::generate()` и trait `AiTask`
  (`src/home_assistant/mod.rs`). Тестовые двойники этого trait есть в десяти
  файлах `tests/`.
- Ответ LLM проходит цепочку «разбор формы (`schema.rs`, `RawItem` со строковыми
  датами) → валидация (`validate.rs`, `DraftItem`) → черновик (`draft.rs`)».
  Черновик хранит `RawItem`, поэтому правки и ответы на вопросы не требуют LLM.
- Уточнения сейчас — строки модели; кнопочные вопросы об исполнителе и дате
  бот строит сам из ошибок валидатора (`telegram/bot/capture/clarify.rs`).
- Квота — число строк `llm_runs` household за 24 часа.
- Readiness сейчас не зависит от LLM.
- Спайк 2026-11-10 (24 фразы; Haiku 5.5 и Gemini 3.5 Flash через OpenRouter,
  llama.cpp с Qwen3.8-4B и Capture-4B-v0.7) установил:
  - три формы элемента (`anyOf`) с датами-выражениями принимают все три
    провайдера, если описание даты вынесено в `$defs` и подключено по `$ref`;
    без этого Anthropic отвечает `400 The compiled grammar is too large`;
  - порядок полей в ответе совпадает с порядком схемы во всех ответах;
  - необученная Qwen3.8-4B: три формы и выражения — 19/24, плоская форма —
    17/24, абсолютные даты — 16/24 с ошибками арифметики дат;
  - облачные модели: 21–24 из 24, p50 2.1–2.4 с, p95 до 4.1 с, у Gemini
    единичные ответы 8.8 с, 14.2 с и таймаут 60 с; локальная модель — p95 1.1 с;
  - у Gemini 3.5 Flash рассуждения нельзя отключить, но
    `reasoning.effort = minimal` даёт 2.3 с вместо 5.2 с; у Haiku параметр
    `provider.require_parameters` приводит к отказу маршрутизации;
  - формат структур Home Assistant не выражает `anyOf` и требует заглушку
    `none` у каждого выбора — слот вида HA потребовал бы второго варианта
    контракта.

## Goals / Non-Goals

**Goals:**

- Один вызов LLM для всех источников, без Home Assistant на пути запроса.
- Контракт, который локальная модель выучит один раз: без арифметики дат, с
  событиями, с недопустимыми сочетаниями, исключёнными схемой.
- Внутреннее представление черновика остаётся прежним по смыслу: новый
  формат ответа — отдельный слой перед существующей валидацией.
- Контракт отрисовывается одним кодом для сервиса, проверки слота и проекта
  дообучения.

**Non-Goals:**

- Слот вида Home Assistant и переменная выбора вида слота: остаётся только
  trait бэкенда как точка расширения.
- Определение подмены модели по полю `model` ответа: провайдеры возвращают
  уточнённые идентификаторы, сравнение дало бы ложные срабатывания.
- Потоковый ответ, повтор запроса к тому же слоту, параллельный опрос слотов.
- Автоматический запуск проверки слота сервисом.

## Decisions

### 1. Клиент и цепочка — новый модуль `src/llm/`

- `ChatBackend` — trait с одним методом: сообщения, схема ответа и таймаут на
  входе; текст ответа, число токенов и модель на выходе. Заменяет `AiTask` и
  остаётся швом для тестовых двойников и будущих видов слота.
- `OpenAiBackend` — единственная реализация: `POST {url}/chat/completions`,
  `response_format = {type: json_schema, json_schema: {name, strict: true,
  schema}}`, `temperature = 0`, верхняя граница `max_tokens`. Дополнительные
  параметры слота (`LLM_*_EXTRA_JSON`) подмешиваются в тело запроса на верхнем
  уровне и не могут заменить `model`, `messages` и `response_format`.
  `provider.require_parameters` не отправляется.
- `Slot` — имя (`primary`, `fallback`), бэкенд, таймаут, собственный
  `CircuitBreaker` (существующий `capture/breaker.rs` используется без
  изменений, по экземпляру на слот).
- `Chain` — исполняет разбор по слотам и возвращает результат вместе со
  списком выполненных попыток для записи в `llm_runs`.

`src/home_assistant/` удаляется целиком. Сохранить `AiTask` и обернуть в него
новый клиент отвергнуто: интерфейс `AiTask` несёт имя задачи и структуру в
формате HA, которые новому клиенту не нужны.

### 2. Конфигурация

| Переменная | Значение |
|---|---|
| `LLM_PRIMARY_URL`, `LLM_FALLBACK_URL` | базовый адрес API, включая `/v1` |
| `LLM_PRIMARY_MODEL`, `LLM_FALLBACK_MODEL` | имя модели |
| `LLM_PRIMARY_TOKEN`, `LLM_FALLBACK_TOKEN` | необязателен |
| `LLM_PRIMARY_TIMEOUT_MS`, `LLM_FALLBACK_TIMEOUT_MS` | по умолчанию 10000 |
| `LLM_PRIMARY_EXTRA_JSON`, `LLM_FALLBACK_EXTRA_JSON` | JSON-объект, необязателен |
| `LLM_CONNECT_TIMEOUT_MS` | по умолчанию 1000 |

`LLM_CAPTURE_ENABLED` и `LLM_DAILY_QUOTA` сохраняются. Невалидный
`*_EXTRA_JSON` — ошибка запуска. Оставшиеся `HA_BASE_URL`, `HA_TOKEN`,
`HA_AI_TASK_ENTITY_ID` дают предупреждение без значений, а не ошибку: это
упрощает откат на предыдущий образ с тем же env-файлом.

### 3. Бюджет и переход между слотами

```
budget = 8 с (ha_voice) | 20 с (остальные)

есть fallback и primary замкнут:
    primary  <= min(timeout_primary, budget / 2)
    fallback <= min(timeout_fallback, budget - потрачено)
primary разомкнут:
    fallback <= min(timeout_fallback, budget)
fallback не настроен:
    primary  <= min(timeout_primary, budget)
```

Переход на резервный слот — при ошибке транспорта, таймауте, любом ответе
`4xx`/`5xx` и при ответе, не прошедшем разбор формы. `400` включён намеренно:
отказ провайдера принять схему детерминирован, и без перехода рабочий
резервный слот не использовался бы. `401`/`403` дополнительно пишутся в лог
уровнем `error`. Превышение числа элементов — ошибка пользователя: перехода
нет, предохранитель не размыкается (как сейчас).

Прежний повтор вызова после некорректного ответа убирается: «два некорректных
ответа» теперь означает по одному от каждого слота. Без резервного слота
некорректный ответ сразу ведёт к деградации — повтор при `temperature = 0`
обычно возвращает тот же ответ.

Цепочка живёт в Tasklerq, а не в `llm-router`: роутер не видит облачные слоты
и недоступен вместе с хостом локальной модели.

### 4. Учёт вызовов и квота

В `llm_runs` добавляются `slot text` и `attempt smallint`; старые строки
остаются с `NULL`. Каждая попытка — отдельная строка, токены берутся из
`usage` ответа. Квота считает строки с `attempt = 1` или `attempt IS NULL`, то
есть разборы. Отдельная таблица попыток отвергнута: `llm_runs` уже несёт все
нужные поля и срок хранения.

### 5. Контракт v4 — слой перед существующей валидацией

```
ответ LLM --(wire: serde, 3 формы)--> выражения
          --(dates: расчёт от now и пояса household)--> RawItem
          --(validate.rs, без изменения смысла)--> DraftItem --> черновик
```

- **Таблица полей** — одно описание полей каждой формы в порядке «сначала
  решения»: `kind`, `list`, `title`, `date`, `time`, (`end`, `end_time`),
  `repeat`, `assignee`, `priority`, (`quantity`, `unit`), `subtasks`, `tags`,
  `notes`, (`note_date`). Из неё строятся и JSON Schema, и примеры промпта —
  пример не может разойтись со схемой.
- **Схема** собирается на запрос: `items` — массив `anyOf` из трёх объектов,
  у каждого все свойства в `required` и `additionalProperties: false`; `list` и
  `assignee` — `enum` из контекста плюс пустая строка; `repeat` —
  `anyOf[object, null]`; описание даты — в `$defs.date`, везде по `$ref`.
  В схеме нет `minimum`, `maxItems`, `pattern`, `oneOf` и `description`:
  пределы проверяет валидатор, правила живут в промпте.
- **Выражение даты** — плоский объект: `kind` (`none`, `offset`, `weekday`,
  `date`, `weekend`, `week`, `month_start`, `month_end`), `n`, `unit`,
  `weekday`, `day`, `month`, `year`; неиспользуемые поля — ноль или пустая
  строка.
- **Разбор формы** — serde с тегом по `kind` и запретом неизвестных полей.
  Тихие компенсации из `schema.rs` (обёртки `{value}`, регистр перечислений,
  строка вместо числа) удаляются: при схеме со строгим режимом они не нужны, а
  их срабатывание означало бы, что слот схему не соблюдает.
- **Имена участников** в `enum` повторяться не могут: одинаковые имена
  схлопываются, неоднозначность, как и сейчас, разрешает валидатор кнопочным
  вопросом.

`RawItem` дополняется концом события (`end_date`, `end_time`) и видом `events`;
строковые абсолютные даты в нём остаются. Черновики, сохранённые прежней
версией, читаются как раньше (новые поля — со значениями по умолчанию) и
истекают за 15 минут.

Плоская форма элемента отвергнута по результатам спайка: хуже качество у малой
модели, больше выходных токенов, недопустимые сочетания пришлось бы ловить
сервером.

### 6. Расчёт дат — `src/capture/dates.rs`

Чистая функция от выражения, роли поля (начало или конец), названного времени,
текущего момента и часового пояса household. Правила перечислены в дельте
`llm-capture` (требования «Даты-выражения», «Расчёт дня недели», «Расчёт
периодов», «Время без даты»). Отдельно:

- у повторения без совместимой даты первое вхождение считает существующий
  `Recurrence::first_due` — все модели в спайке ставили датой первый названный
  день недели, а не ближайшее вхождение;
- время конца без даты относится к дню начала, не позже времени начала — к
  следующему дню (то же правило, что в редакторе события);
- вторая дата превращается в текст «20 ноября» (с годом, если он не текущий)
  и дописывается к заметке через пробел;
- недопустимое выражение (31 февраля, неизвестный день недели) даёт ошибку
  элемента, а не ошибку разбора: остальные элементы черновика сохраняются.

Противоречие «время без даты уже прошло» снимается: такое время переносится
на завтра, а ошибка «время уже прошло» остаётся только для явно названного
«сегодня».

### 7. Уточнения

`clarifications` — пары «номер элемента, тема» с темами `date`, `time`,
`assignee`, `list`. Тема `repeat` из черновика контракта исключена: кнопочного
ответа для неё нет, а нереализуемая тема ухудшила бы и схему, и разметку.

Сервер сопоставляет уточнение с элементом и отбрасывает его, если поле уже
заполнено. Вопросы о дате и исполнителе — существующие экраны `clarify.rs`;
добавляются вопрос о списке (кнопки списков нужного типа) и о времени («Весь
день» и ввод времени текстом). Вопросы из ошибок валидатора остаются и имеют
приоритет над уточнениями модели. В хранимом черновике уточнения становятся
структурой; строки прежнего формата при чтении отбрасываются. Угадывание темы
по словам вопроса в `eval.rs` удаляется.

### 8. Промпт

Шаблон `src/capture/prompts/capture-v4.txt`: статичные правила и примеры в
начале системного сообщения, изменяемый контекст (текущий момент, списки с
типами, участники, автор) — в конце; текст пользователя — отдельным сообщением
в разделителях. Блока «Ближайшие дни» нет. Правила переносятся из
`tasklerq-capture-ft/docs/label-contract.md` и из промпта спайка; к ним
добавляется: дата у повторения — только если начало названо. Шаблоны и снимки
`capture-v1`…`v3` удаляются.

Хеш контракта — SHA-256 от шаблона и схемы для канонического контекста; тест
снимка требует смены версии при изменении любого из них.

### 9. `capture-render`

Читает JSONL из стандартного ввода (`id`, `context`, `text`), пишет JSONL
(`id`, `messages`, `schema`, `prompt_version`, `contract_hash`). Использует ту
же функцию сборки запроса, что и разбор; база и сеть не нужны. Проект
дообучения сверяет `contract_hash` в манифесте датасета.

### 10. Smoke-набор и проверка слота

- Набор `tests/golden/smoke-v4.json`: около 22 фраз — по две на категорию
  прежнего набора, события и прямое добавление покупок. Эталоны готовит более
  сильная модель через `capture-render`, затем их проверяет человек, после
  чего файл замораживается. `tests/golden/capture.json`, `baseline.json` и
  `tests/golden_capture.rs` удаляются.
- `eval.rs` переписывается: сравнение ведётся над `DraftItem` после расчёта
  дат при фиксированном «сейчас» набора; причины провала — по требованию
  «Причины провала и оценка задержки». Названия сравниваются как множества
  основ слов (стеммер Snowball, зависимость `rust-stemmers`); поле
  `alt_titles` не вводится.
- `tasklerq capture-eval --slot <имя>` читает конфигурацию слота из окружения,
  ждёт каждую фразу до 20 секунд, судит по таймауту слота и пишет результат в
  таблицу `llm_slot_checks`: слот, отпечаток, части отпечатка, число
  пройденных и всех фраз, p95, отчёт в JSON, время. Хранится последняя запись
  на слот.
- Статус слота вычисляется сравнением отпечатка действующей конфигурации с
  сохранённым: при старте (лог) и в readiness с кешем на минуту. Метрика
  `llm_slot_verified{slot}` — 1 только для статуса «прошёл».

### 11. Readiness не падает из-за LLM

В заметках к обсуждению было «readiness падает, когда мертвы оба слота». В
design это заменено предупреждением: при отказе LLM сервис работает с
деградацией (редактор с исходным текстом, fallback-позиция), а провал
readiness вывел бы из работы и то, что от LLM не зависит. Предупреждения —
`llm_unavailable` и `llm_slot_unverified`.

### 12. События в черновике и применении

`DraftItem` несёт конец события; карточка черновика показывает начало и
конец; «Изменить» открывает редактор события из `0009-events`. Применение
создаёт событие через тот же путь домена, что редактор и API, — правила полей
события проверяются там же. Исключение списков событий в `context.rs` и отказ
`422` во внешнем capture убираются; подсказка `hint` не расширяется. Событие
без начала в режиме `auto` ведёт к обычной деградации, а не к созданию события
«на сегодня».

## Risks / Trade-offs

- [Локальная модель до переобучения не знает v4: Capture-4B-v0.7 путает
  событие с задачей] → до переобучения основной слот — облачная модель;
  локальную можно включать после проверки `capture-eval`. Описывается в
  `docs/llm-capture.md`.
- [Провайдер отклоняет схему (`400`) при росте числа списков или смене
  версии API] → переход на резервный слот, ошибка в логе; проверка слота
  включает household с 20 списками и 8 участниками.
- [Хвосты задержки у облачных моделей до десятков секунд] → бюджет слота и
  резервный слот; для голоса основной ограничен 4 секундами.
- [Около 5–7 тысяч входных токенов на разбор] → статичная часть промпта стоит
  первой и кешируется провайдером; стоимость и квота описаны в документации.
- [Текст пользователя уходит провайдерам обоих слотов] → раскрывается в
  документации; конфигурация с одним локальным слотом не выпускает текст из
  сети.
- [Большая правка тестов: двойники `AiTask` в десяти файлах отдают ответы v3]
  → общий двойник бэкенда и построитель ответа v4 в `tests/support`.
- [Эталоны smoke-набора зависят от ручной проверки] → отдельная задача с
  явным результатом; до неё проверка слота недоступна, работа слотов — нет.
- [Стеммер сравнивает основы, а не леммы: «оплата» и «оплатить» могут не
  совпасть] → эталонные названия пишутся в форме, предписанной правилами
  (инфинитив, именительный падеж); расхождение формы — законный `mismatch`.

## Migration Plan

1. Миграция `0018`: колонки `slot`, `attempt` в `llm_runs`; таблица
   `llm_slot_checks`. Миграция аддитивная, предыдущий образ на ней работает.
2. В env-файл добавляются `LLM_PRIMARY_*` (и при необходимости
   `LLM_FALLBACK_*`); `HA_*` остаются на время перехода.
3. Развёртывание образа. Черновики, созданные до него, истекают за 15 минут.
4. `tasklerq capture-eval --slot primary` (и `fallback`) в контейнере; при
   статусе «не прошёл» — смена модели или параметров слота.
5. После подтверждения работы `HA_*` удаляются из env-файла, а токен HA
   отзывается в Home Assistant.

Откат: предыдущий образ с тем же env-файлом — он читает `HA_*`, пока они не
удалены на шаге 5.

## Open Questions

- Состав пары слотов по умолчанию в документации (например, Haiku 5.5
  основным и Gemini 3.5 Flash резервным) — выбирается по результатам
  `capture-eval` после реализации; на код не влияет.
