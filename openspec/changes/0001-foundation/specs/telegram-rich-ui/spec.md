## Purpose

Описывает Telegram-интерфейс Tasklerq: приватный чат, RichMessage-экраны с
кнопками, навигацию с редактированием сообщений, обработку callback-действий и
надёжную доставку обновлений.

## ADDED Requirements

### Requirement: Только приватные чаты

Система SHALL обслуживать только приватные чаты Telegram. Обновления из групп,
супергрупп и каналов MUST игнорироваться; при первом обращении в группе бот может
отправить одно пояснение, что работа возможна только в личном чате. Данные
группы MUST не сохраняться.

#### Scenario: Личный чат

- **WHEN** пользователь отправляет сообщение боту в приватном чате
- **THEN** система обрабатывает его как действие пользователя
- **AND** привязывает чат к household пользователя

#### Scenario: Групповой чат

- **WHEN** бот получает обновление из группы
- **THEN** система не создаёт задачи и не сохраняет содержимое сообщения
- **AND** завершает обработку без ошибки

### Requirement: RichMessage-экраны

Система SHALL отображать главное меню, списки, карточки задач, результаты
поиска и подтверждения черновиков как RichMessage-сообщения с HTML-контентом и
кнопками внутри содержимого. Кнопки MUST иметь callback-токен и MUST быть
доступны без внешней inline-клавиатуры. Отдельный запасной режим без
RichMessage не предусматривается.

#### Scenario: Список задач в RichMessage

- **WHEN** пользователь открывает список задач
- **THEN** бот отправляет RichMessage с заголовком, счётчиками и кнопками
  задач и навигации
- **AND** кнопки находятся внутри содержимого сообщения

#### Scenario: Экранирование пользовательского текста

- **WHEN** в названии задачи есть символы `<`, `>` или `&`
- **THEN** бот экранирует их в HTML
- **AND** название отображается буквально, без выполнения разметки

### Requirement: Редактирование и навигация

Система SHALL использовать одно активное сообщение на поток навигации: переход
вперёд, назад и обновление экрана MUST редактировать существующее сообщение, а
не отправлять новое. Если редактирование невозможно, система MUST заменить
сообщение (удалить старое и отправить новое) ровно один раз. Навигация MUST
поддерживать возврат в главное меню, пагинацию списков и обновление после
действия.

#### Scenario: Переход в карточку задачи

- **WHEN** пользователь нажимает кнопку задачи в списке
- **THEN** бот редактирует текущее сообщение, показывая карточку задачи
- **AND** в чате не появляется второе активное сообщение

#### Scenario: Возврат назад

- **WHEN** пользователь нажимает «Назад» в карточке задачи
- **THEN** бот редактирует сообщение, возвращая список на прежнюю позицию
- **AND** счётчики отражают актуальное состояние

#### Scenario: Устаревшая кнопка

- **WHEN** пользователь нажимает кнопку от ранее заменённого сообщения
- **THEN** система показывает всплывающее уведомление об устаревшем действии
- **AND** обновляет активный экран без дублирования сообщений

### Requirement: Callback-токены

Система SHALL кодировать callback-действия непрозрачными одноразовыми токенами
длиной не более 64 байт в поле `callback_data`. Токен MUST быть привязан к
пользователю, household, действию, полезной нагрузке и версии ресурса, а также
MUST иметь срок жизни не более 24 часов. Повторное использование, истечение
или несовпадение пользователя MUST приводить к отказу без выполнения действия.
Потребление токена MUST быть атомарным.

#### Scenario: Корректное действие

- **WHEN** пользователь нажимает кнопку с действительным токеном
- **THEN** система проверяет пользователя и выполняет действие один раз
- **AND** помечает токен использованным

#### Scenario: Повторное нажатие

- **WHEN** пользователь повторно нажимает ту же кнопку
- **THEN** система не выполняет действие повторно
- **AND** показывает актуальное состояние ресурса

#### Scenario: Чужой токен

- **WHEN** другой пользователь пытается использовать callback-токен
- **THEN** система отклоняет действие
- **AND** не раскрывает данные исходного пользователя

#### Scenario: Истёкший токен

- **WHEN** пользователь нажимает кнопку со токеном старше 24 часов
- **THEN** система показывает сообщение об истечении действия
- **AND** предлагает открыть актуальный экран

### Requirement: Главное меню

Система SHALL показывать в главном меню количество открытых задач, количество
просроченных задач, количество невыполненных позиций покупок и список
доступных списков. Меню MUST содержать кнопки «Задачи», «Покупки», «Добавить»,
«Мои задачи», «Поиск» и «Настройки». Счётчики MUST обновляться после каждого
действия, изменяющего состояние.

#### Scenario: Открытие меню

- **WHEN** пользователь отправляет `/start` или нажимает «В меню»
- **THEN** бот показывает главное меню с актуальными счётчиками
- **AND** кнопки ведут в соответствующие разделы

#### Scenario: Обновление счётчиков

- **WHEN** пользователь завершает задачу и возвращается в меню
- **THEN** счётчик открытых задач уменьшается на единицу
- **AND** счётчик завершённых за день обновляется

### Requirement: Пошаговые формы

Система SHALL поддерживать пошаговые формы создания и редактирования задачи
или позиции. Состояние формы MUST храниться в базе и MUST быть привязано к
чату и пользователю; срок жизни состояния — не более 15 минут. Пользователь
MUST иметь возможность отменить форму на любом шаге. Валидация MUST происходить
до сохранения; при ошибке форма остаётся открытой с пояснением. Одновременно у
пользователя может быть только одна активная форма.

#### Scenario: Создание задачи через форму

- **WHEN** пользователь выбирает «Добавить» → «Задачу» и заполняет название,
  срок и приоритет
- **THEN** система показывает предпросмотр
- **AND** после подтверждения создаёт задачу и возвращает в список

#### Scenario: Некорректная дата

- **WHEN** пользователь вводит дату в неверном формате
- **THEN** бот показывает пример корректного формата
- **AND** форма остаётся открытой без потери введённых данных

#### Scenario: Отмена формы

- **WHEN** пользователь нажимает «Отмена»
- **THEN** состояние формы удаляется
- **AND** бот возвращает предыдущий экран

#### Scenario: Истечение формы

- **WHEN** пользователь возвращается к форме спустя 15 минут
- **THEN** система сообщает, что форма устарела
- **AND** предлагает начать заново

### Requirement: Обработка webhook-обновлений

Система SHALL принимать обновления Telegram через webhook, проверять секрет и
сохранять обновление в очередь PostgreSQL до отправки ответа `200 OK`. Ответ
MUST быть отправлен не позднее чем через 5 секунд после получения запроса.
Обновления MUST обрабатываться идемпотентно по `update_id`: повторная доставка
MUST не создавать повторных эффектов. При временной ошибке обработки система
MUST повторять попытку с экспоненциальной задержкой; после исчерпания попыток
обновление MUST попадать в очередь ошибок с диагностикой.

#### Scenario: Дубликат обновления

- **WHEN** Telegram повторно доставляет обновление с тем же `update_id`
- **THEN** система сохраняет только одну запись
- **AND** не выполняет действие повторно

#### Scenario: Временная ошибка

- **WHEN** обработка обновления завершается временной ошибкой базы
- **THEN** система повторяет попытку с задержкой
- **AND** после успеха применяет действие ровно один раз

#### Scenario: Исчерпание попыток

- **WHEN** обновление не удалось обработать после максимального числа попыток
- **THEN** оно помечается как ошибочное
- **AND** метрика ошибок увеличивается
- **AND** пользователь не получает частично применённое действие

### Requirement: Исходящие сообщения и лимиты

Система SHALL отправлять исходящие сообщения через outbox с повторными
попытками. При ответе Telegram `429 Too Many Requests` система MUST
использовать `retry_after` и не отправлять сообщение раньше указанного времени.
Система MUST соблюдать не более одного сообщения в секунду в один чат и не
более 30 сообщений в секунду суммарно. Повторная отправка MUST не создавать
видимых дубликатов, если предыдущая попытка уже доставила сообщение.

#### Scenario: Ограничение Telegram

- **WHEN** Telegram возвращает `429` с `retry_after = 5`
- **THEN** система откладывает сообщение минимум на 5 секунд
- **AND** не теряет его из outbox

#### Scenario: Недоступность Telegram

- **WHEN** Telegram API временно недоступен
- **THEN** система повторяет отправку с экспоненциальной задержкой
- **AND** сохраняет порядок сообщений в чате

#### Scenario: Защита от дублей

- **WHEN** воркер повторяет отправку после сбоя, когда сообщение уже доставлено
- **THEN** система использует сохранённый `message_id` и не отправляет копию
- **AND** при необходимости редактирует существующее сообщение

### Requirement: Ошибки и пустые состояния

Система SHALL показывать пользователю понятные сообщения об ошибках на русском
языке без стектрейсов, идентификаторов внутренних ошибок и секретов. Пустые
списки MUST содержать пояснение и кнопку добавления. Ошибки валидации MUST
указывать, какое поле нужно исправить. При недоступности LLM или Home Assistant
бот MUST предложить доступный ручной сценарий.

#### Scenario: Пустой список

- **WHEN** пользователь открывает пустой список задач
- **THEN** бот показывает «Пока нет задач» и кнопку «Добавить»
- **AND** не показывает пустую таблицу

#### Scenario: Внутренняя ошибка

- **WHEN** операция завершается внутренней ошибкой
- **THEN** бот показывает нейтральное сообщение с просьбой повторить позже
- **AND** записывает диагностику без пользовательских данных

### Requirement: Локализация и форматирование

Интерфейс бота MUST быть на русском языке в MVP. Даты MUST отображаться в
часовом поясе пользователя в человекочитаемом виде («сегодня», «завтра»,
«пн, 3 ноя», «3 ноя 2026, 18:00»). Система MUST корректно склонять
существительные для количеств и MUST использовать UTF-8 во всех сообщениях.
Названия кнопок и сообщения об ошибках MUST не содержать английских
служебных строк, кроме технических идентификаторов, явно показанных
пользователю.

#### Scenario: Человекочитаемая дата

- **WHEN** задача назначена на завтра
- **THEN** бот показывает «завтра» вместо полной даты
- **AND** во всплывающей подсказке доступна полная дата

#### Scenario: Склонение количества

- **WHEN** в списке одна, две или пять задач
- **THEN** бот использует формы «задача», «задачи», «задач» соответственно
- **AND** не показывает «1 задач»
