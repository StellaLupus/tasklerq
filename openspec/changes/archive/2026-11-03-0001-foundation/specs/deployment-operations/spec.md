## Purpose

Описывает развёртывание и эксплуатацию Tasklerq: конфигурацию, PostgreSQL,
Docker, Telegram webhook, health, фоновые задания, обновления, резервное
копирование и локальную разработку.

## ADDED Requirements

### Requirement: Конфигурация через окружение

Система SHALL читать конфигурацию из переменных окружения и MUST завершать
запуск с понятной ошибкой, если отсутствует обязательный параметр или он
невалиден. Обязательные параметры MUST включать `DATABASE_URL` и
`PUBLIC_BASE_URL`; при `TELEGRAM_MODE=webhook` — `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_WEBHOOK_SECRET`; при включённом LLM — параметры подключения к Home
Assistant. Режим `TELEGRAM_MODE=disabled` MUST позволять запуск без Telegram и
без `TELEGRAM_BOT_TOKEN`. Параметры внешнего capture MUST включать
`CAPTURE_API_ENABLED`, `CAPTURE_VOICE_TIMEOUT_MS`, `CAPTURE_VOICE_FALLBACK_RAW`,
`CAPTURE_RATE_LIMIT_PER_MIN` и `CAPTURE_MAX_TEXT_CHARS`. Секреты MUST NOT
храниться в репозитории и MUST NOT выводиться в лог при старте. Значения по
умолчанию MUST быть безопасными: сервис не должен запускаться в production без
webhook-секрета, если Telegram включён.

#### Scenario: Отсутствует DATABASE_URL

- **WHEN** сервис запускается без `DATABASE_URL`
- **THEN** процесс завершается с кодом ошибки
- **AND** сообщение указывает отсутствующий параметр
- **AND** секреты не выводятся

#### Scenario: Невалидный URL

- **WHEN** `PUBLIC_BASE_URL` не является HTTPS-URL в production
- **THEN** сервис отказывается запускаться
- **AND** сообщает ожидаемый формат

#### Scenario: Секреты не логируются

- **WHEN** сервис стартует с корректной конфигурацией
- **THEN** лог содержит имена параметров и версию
- **AND** не содержит значений токенов и паролей

#### Scenario: Headless-режим без Telegram

- **WHEN** сервис запускается с `TELEGRAM_MODE=disabled` без
  `TELEGRAM_BOT_TOKEN`
- **THEN** сервис стартует
- **AND** HTTP API и внешний capture работают
- **AND** webhook и исходящие сообщения отключены

#### Scenario: Capture отключён

- **WHEN** `CAPTURE_API_ENABLED=false`
- **THEN** эндпоинты capture возвращают `503`
- **AND** остальные API продолжают работать

### Requirement: PostgreSQL

Система SHALL использовать PostgreSQL версии 15 или новее как единственное
хранилище данных. Подключение MUST осуществляться через пул соединений
размером от 5 до 20; `statement_timeout` MUST быть ограничен. Миграции MUST
применяться при старте под advisory lock или отдельной командой и MUST быть
совместимы с предыдущей версией приложения на время обновления. При
недоступности базы readiness MUST возвращать ошибку, а сервис MUST NOT
принимать пользовательские запросы.

#### Scenario: Применение миграций

- **WHEN** сервис запускается на пустой базе
- **THEN** миграции применяются по порядку
- **AND** повторный запуск не применяет их повторно

#### Scenario: Ошибка миграции

- **WHEN** миграция завершается ошибкой
- **THEN** сервис не запускается в рабочий режим
- **AND** в логе указана миграция и причина
- **AND** данные не остаются в частично изменённом состоянии

#### Scenario: База недоступна

- **WHEN** PostgreSQL недоступен
- **THEN** `/health/ready` возвращает ошибку
- **AND** webhook не подтверждает обработку обновлений

### Requirement: Docker-развёртывание

Система SHALL поставляться в виде Docker-образа, запускаемого от непривилегированного
пользователя. Образ MUST содержать healthcheck, MUST поддерживать graceful
shutdown и MUST не требовать записи в корневую файловую систему. Пример
Docker Compose MUST описывать сервис Tasklerq, внешнюю сеть для PostgreSQL и
Home Assistant, публикацию порта только на loopback и ограничение ресурсов.
Секреты MUST передаваться через env-file с ограниченными правами или Docker
secrets.

#### Scenario: Запуск контейнера

- **WHEN** контейнер запускается с корректным env-file
- **THEN** сервис становится healthy
- **AND** порт доступен только через reverse proxy

#### Scenario: Graceful shutdown

- **WHEN** контейнер получает `SIGTERM`
- **THEN** сервис перестаёт принимать новые задания
- **AND** завершает текущие операции в течение 30 секунд
- **AND** очередь не теряет обновления

#### Scenario: Read-only filesystem

- **WHEN** контейнер запущен с `read_only: true`
- **THEN** сервис работает, используя tmpfs для временных файлов
- **AND** не пытается писать в корень образа

### Requirement: Telegram webhook и TLS

Система SHALL принимать webhook по HTTPS-адресу `PUBLIC_BASE_URL` и пути
`/webhooks/telegram`. Запрос MUST проверять заголовок
`X-Telegram-Bot-Api-Secret-Token` сравнением с секретом за постоянное время;
несовпадение MUST возвращать `401` без деталей. Размер тела MUST быть ограничен
1 МБ. В production режим polling MUST быть запрещён; polling может использоваться
только в development. Система MUST регистрировать webhook при старте, если
задан `TELEGRAM_WEBHOOK_URL`, и MUST логировать результат без токена.

#### Scenario: Регистрация webhook

- **WHEN** сервис стартует с `TELEGRAM_WEBHOOK_URL`
- **THEN** он вызывает `setWebhook` с секретом и списком допустимых обновлений
- **AND** логирует успешный результат

#### Scenario: Неверный секрет

- **WHEN** запрос приходит без корректного секрета
- **THEN** сервис возвращает `401`
- **AND** обновление не сохраняется

#### Scenario: Polling в production

- **WHEN** `TELEGRAM_MODE=polling` при `ENV=production`
- **THEN** сервис отказывается запускаться
- **AND** сообщает использовать webhook

### Requirement: Health и наблюдаемость

Система SHALL предоставлять `/health/live` для проверки процесса и
`/health/ready` для проверки базы, применённых миграций и допустимой задержки
очередей. Логи MUST быть структурированными JSON и MUST содержать `request_id`,
`update_id` (для webhook), длительность и результат операции. Логи MUST NOT
содержать текст сообщений, токены и персональные данные. Система MUST
предоставлять метрики количества обновлений, ошибок, задержки очередей, LLM и
доставки; метрики MUST быть защищены от публичного доступа.

#### Scenario: Успешная readiness

- **WHEN** база доступна, миграции применены, очередь не переполнена
- **THEN** `/health/ready` возвращает `200`
- **AND** содержит версию и время проверки

#### Scenario: Переполненная очередь

- **WHEN** задержка очереди превышает настроенный порог
- **THEN** `/health/ready` возвращает ошибку
- **AND** метрика задержки отражает значение

#### Scenario: Логи без PII

- **WHEN** пользователь отправляет задачу с названием «Купить лекарство»
- **THEN** лог содержит идентификатор обновления и результат
- **AND** не содержит название задачи

### Requirement: Фоновые задания

Система SHALL выполнять обработку Telegram-обновлений, отправку outbox,
напоминания и очистку данных через фоновые воркеры в том же процессе. Задания
MUST захватываться через `FOR UPDATE SKIP LOCKED` или эквивалентный механизм,
безопасный для нескольких экземпляров. Воркеры MUST поддерживать retry с
экспоненциальной задержкой и MUST корректно завершаться при остановке.
Повторная обработка задания MUST быть идемпотентной.

#### Scenario: Падение воркера

- **WHEN** воркер завершается во время обработки обновления
- **THEN** задание возвращается в очередь после истечения блокировки
- **AND** обрабатывается другим воркером
- **AND** эффект применяется один раз

#### Scenario: Остановка сервиса

- **WHEN** сервис получает сигнал остановки
- **THEN** воркеры завершают текущие задания
- **AND** незавершённые задания остаются в очереди

#### Scenario: Несколько экземпляров

- **WHEN** запущены два экземпляра сервиса
- **THEN** каждое задание обрабатывается только одним экземпляром
- **AND** дубликаты не возникают

### Requirement: Обновления и откат

Система SHALL публиковать версионированные Docker-образы с тегом semver и
git SHA. Миграции MUST следовать схеме expand/contract: сначала добавляются
совместимые изменения, затем удаляются устаревшие в следующем релизе. Откат
MUST быть возможен на предыдущий образ без потери данных. Перед обновлением
MUST создаваться резервная копия базы. Разрушительные миграции MUST NOT
выполняться в том же релизе, что и код, который перестаёт использовать старые
поля.

#### Scenario: Обновление

- **WHEN** развёртывается новая версия
- **THEN** миграции применяются до запуска нового кода
- **AND** сервис проходит readiness
- **AND** старые данные остаются доступными

#### Scenario: Откат

- **WHEN** новая версия не проходит проверку
- **THEN** развёртывается предыдущий образ
- **AND** схема остаётся совместимой
- **AND** данные не теряются

#### Scenario: Разрушительная миграция

- **WHEN** релиз содержит удаление колонки, используемой предыдущей версией
- **THEN** релиз отклоняется на этапе проверки
- **AND** удаление переносится в следующий релиз

### Requirement: Резервное копирование и retention

Система SHALL документировать и поддерживать ежедневное резервное копирование
PostgreSQL с хранением не менее 14 дней и выносом копии за пределы хоста.
Восстановление MUST быть проверено не реже одного раза в квартал. Система MUST
удалять `telegram_updates` через 7 дней, черновики capture через 30 дней,
`llm_runs` через 90 дней, события задач через 365 дней, мягко удалённые задачи
через 30 дней и отправленный outbox через 30 дней. Сроки MUST быть
конфигурируемыми.

#### Scenario: Ежедневная копия

- **WHEN** наступает время backup
- **THEN** создаётся дамп базы
- **AND** копия сохраняется вне хоста
- **AND** ошибка backup увеличивает метрику

#### Scenario: Восстановление

- **WHEN** база потеряна
- **THEN** последний дамп восстанавливается в новую базу
- **AND** сервис проходит readiness
- **AND** данные задач и household доступны

#### Scenario: Очистка старых данных

- **WHEN** фоновое задание retention запускается
- **THEN** удаляются записи старше настроенных сроков
- **AND** активные задачи и household не затрагиваются

### Requirement: Локальная разработка

Система SHALL предоставлять локальную конфигурацию Docker Compose с
PostgreSQL и возможностью запуска Telegram в режиме polling. Для разработки
MUST быть доступны подмена Telegram API и Home Assistant через локальные
mock-серверы, seed-данные и интеграционные тесты. Запуск MUST не требовать
публичного домена и production-секретов.

#### Scenario: Локальный запуск

- **WHEN** разработчик запускает `docker compose up` в dev-режиме
- **THEN** поднимается PostgreSQL и сервис
- **AND** бот работает через polling с тестовым токеном

#### Scenario: Моки внешних систем

- **WHEN** запускаются интеграционные тесты
- **THEN** Telegram и Home Assistant заменены mock-серверами
- **AND** тесты не обращаются в интернет

### Requirement: Административный CLI

Система SHALL предоставлять CLI `tasklerq admin` для создания и отзыва API-
токенов, просмотра статистики очередей, проверки webhook, списка household,
создания household и добавления пользователя по Telegram ID с ролью `owner` или
`member` (для режима без онбординга в боте). Токены и пользователи принадлежат
household: `--household` MAY опускаться, если household единственный. Добавление
пользователя MUST записывать событие `member_joined`, отклонять Telegram ID,
уже состоящий в другом household, и второго `owner`. Команды MUST
работать с той же конфигурацией, что и сервис. Опасные команды
(отзыв токена, удаление household) MUST требовать явного подтверждения.
Вывод MUST NOT содержать секреты и полные токены; новый токен показывается
один раз.

#### Scenario: Создание токена

- **WHEN** администратор выполняет `tasklerq admin token create --name "Home Assistant" --scopes ha:read,ha:write`
- **THEN** CLI выводит токен один раз
- **AND** в базе сохраняется только хеш
- **AND** повторный вывод невозможен

#### Scenario: Household без Telegram

- **WHEN** администратор выполняет
  `tasklerq admin household create --name "Семья" --timezone Europe/Moscow`
- **THEN** создаются household и списки «Задачи» и «Покупки»
- **AND** CLI выводит идентификатор household для создания токенов

#### Scenario: Добавление владельца по Telegram ID

- **WHEN** администратор выполняет
  `tasklerq admin user add --telegram-id 123456789 --role owner --name "Алексей"`
- **THEN** в единственном household появляется владелец с этим Telegram ID
- **AND** в журнале членства есть событие `member_joined` с источником CLI

#### Scenario: Telegram ID уже занят

- **WHEN** администратор добавляет Telegram ID, который состоит в другом household
- **THEN** CLI завершается ошибкой и ничего не меняет

#### Scenario: Статистика очередей

- **WHEN** администратор выполняет `tasklerq admin queue stats`
- **THEN** CLI показывает количество ожидающих, обрабатываемых и ошибочных
  заданий
- **AND** не показывает содержимое сообщений

#### Scenario: Опасная команда

- **WHEN** администратор пытается отозвать токен без флага подтверждения
- **THEN** CLI запрашивает подтверждение
- **AND** без подтверждения ничего не меняет
