# Design

## Context

- Правило получателя зашито в двух местах: при планировании
  (`plan_reminders`, `COALESCE(i.assignee_user_id, i.created_by_user_id)` в
  `src/jobs/scheduler.rs`) и при проверке устаревания перед доставкой
  (`NoticeRow::recipient_selected` в `src/jobs/notice.rs`). Ключ доставки уже
  включает пользователя, поэтому «каждому ровно одно сообщение» обеспечено.
  `reminder_stale` для snooze сверяет только `origin_key`, без получателя.
  Уведомление о назначении устаревает, если исполнитель сменился
  (`assignment_stale`), но только пока оно не отправлено.
- «Мои задачи»: счётчик — `items::open_assigned_tasks`, экран — `mine()` через
  `SearchFilters { assignee_user_id }` (позиционные параметры в
  `SEARCH_FILTERS`, `find.rs`), лимит `MAX_LIMIT` = 50, пустой экран — «Вам
  пока ничего не назначено». Тот же фильтр обслуживает HTTP API.
- `members::detach` при исключении участника снимает его с задач
  (`assignee_user_id = NULL`) — по новому правилу они становятся общими.
- Выполнение — событие `completed` в `item_events` с `actor_user_id` и
  плановым сроком (`items::completions`, `Completion.due_at`); выполнение
  считается действующим по `COMPLETION_SELECTION` (не отменено событием с
  `undo_of` и не снято `reopened`). `items::complete` возвращает `Item`, а не
  событие. Окно отмены — 10 минут.
- Отправленные уведомления: `notification_deliveries` со `status = 'sent'` и
  `outbox_seq`; у строки outbox после доставки есть `message_id` и `sent_at`.
  Блоки сводного сообщения связаны с `notification_batches` (`batch_id`).
- `Outgoing::Edit` доставляется через `replace_or_send`: если сообщения уже
  нет (`MessageGone`), outbox удаляет его и **присылает правку новым
  сообщением**, помечая вид чата засыпанным.
- Из 0017: отложенное удаление с ключом `notice-expire:` и
  `outbox::cancel_scheduled_deletes`, удаления уборки (`cleanup`), отметка
  `dismissed_at` у убранных и заменённых уведомлений (в том числе исходного
  напоминания, чьё «😴 Напомню …» заменено или снято), `notify::show_done`
  с автоудалением своего сообщения, «🗑 Убрать» по истёкшему токену.
- Планировщик тикает раз в 30 секунд, шаги независимы.

## Goals / Non-Goals

**Goals:**
- Одно правило «нет исполнителя — общая» для получателей и «Моих задач».
- Отправленные уведомления не остаются с рабочими кнопками после выполнения
  задачи любым путём (бот, API, HA) или после её назначения другому
  участнику — оба случая обрабатываются одним механизмом.
- Синхронизация никогда не возвращает в чат сообщение, которое уже убрано —
  кнопкой, заменой или руками пользователя.

**Non-Goals:**
- Новое поле «общая» у задачи.
- Изменение фильтра по исполнителю в HTTP API и поиске.
- Синхронизация блоков сводного сообщения (они и так перерисовываются по
  актуальному состоянию при нажатии).
- Уведомление участников о выполнении, если напоминание им не приходило.
- Отмена выполнения или назначения из перерисованной копии.
- Синхронизация напоминаний о событиях при смене участника.

## Decisions

### 1. Получатель: `assignee_user_id` вместо `COALESCE(assignee, author)`

В `plan_reminders` выбор становится `i.assignee_user_id AS selected_user_id`;
`recipient_selected` сравнивает только с исполнителем, без исполнителя — `true`.
Следствия, которые проверяются тестами: назначение общей задачи отменяет
ещё не отправленные напоминания остальным (они устаревают); снятие
исполнителя добавляет напоминания остальным на следующем тике (`NOT EXISTS`
по пользователю); исключение участника из household (`detach`) делает его
задачи общими. Событие без участника, чьё оно, получает каждый участник.

Snooze тоже начинает проверять получателя: `reminder_stale` для snooze
устаревает, если у задачи есть исполнитель и это не получатель. Иначе копия
у Пети закрылась бы как «👤 Назначено: … · Маша» (решение 4), а через час ему
же пришло бы отложенное напоминание о чужой задаче. Сообщение «😴 Напомню …»
отменённого snooze снимает 0017.

### 2. «Мои задачи»: отдельный фильтр `mine_for`

`SearchFilters` получает `mine_for: Option<Uuid>` с предикатом
`(i.assignee_user_id = $x OR i.assignee_user_id IS NULL)`; `assignee_user_id`
остаётся буквальным, HTTP API его не меняет. Предикат — один SQL-фрагмент,
его же использует `items::open_mine_tasks` (замена `open_assigned_tasks`) и
выборка сводки 0019. Новый параметр сдвигает позиционные привязки
`SEARCH_FILTERS` — тесты фильтров обновляются. Меню и заголовок экрана
считают по новому предикату; лимит экрана прежний. Пустой экран: «Нет ни
ваших, ни общих задач». Отметка «👥» добавляется в подпись строки на экране
«Мои задачи», если у задачи нет исполнителя; `task_label` для других экранов
не меняется.

Альтернатива — два раздела «Мои» и «Общие». Отклонена: экран уже разбит по
срокам («Просрочено», «Сегодня»…), второе измерение разделов делает его
длинным.

### 3. Правка без повторной отправки — `Outgoing::Edit { …, resend_if_gone }`

Поле в payload, у старых строк отсутствует → `true` (прежнее поведение). Для
`resend_if_gone = false` доставка при `MessageGone` завершается как `sent`
без отправки и без `mark_buried`. Все правки по инициативе планировщика
(этот шаг, `sync_digests` в 0019) идут с `false`: сообщение, удалённое
пользователем вручную (о таком удалении бот не узнаёт), не возвращается.

### 4. Синхронизация отправленных уведомлений — шаг планировщика

Новый шаг тика `sync_completed_notices`. Он, а не обработчики выполнения,
выбран потому, что задачу выполняют из разных мест: бот (карточка, список,
уведомление, сводное), HTTP API, Home Assistant. Задержка до 30 секунд
приемлема.

Миграция `0026_notice_closed.sql`: `notification_deliveries.closed_at
timestamptz NULL`, `closed_reason text NULL` (`completed` | `assigned`, CHECK),
`closed_by_event uuid NULL REFERENCES item_events (id) ON DELETE SET NULL`
(выполнение, по которому сообщение закрыто; для `assigned` пусто) и частичный
индекс `(updated_at) WHERE status = 'sent'` под выборку шага.

Кандидаты — доставки `reminder`, `snooze`, `assignment`:
`status = 'sent'`, `batch_id IS NULL`, `dismissed_at IS NULL`, задача не
событие, `outbox.message_id IS NOT NULL`, `outbox.sent_at` не старше 47 часов
(автоудаление должно успеть до лимита Telegram в 48 часов), получатель жив,
в том же household и с чатом (те же условия, что `NoticeRow::recipient_alive`).
Выборка ограничена `updated_at` за 48 часов.

Для каждой (своя транзакция, `FOR UPDATE SKIP LOCKED` по записи доставки):

- **Закрыть по выполнению.** `closed_at IS NULL` и есть действующее выполнение задачи,
  созданное после постановки доставки в outbox (`outbox.created_at` — не
  `sent_at`, иначе выполнение, пока сообщение стояло в очереди, потерялось
  бы), чьё вхождение совпадает с доставкой: для `reminder` — `occurrence_key`
  из `Completion.due_at` (сравнение разобранных значений, не строк); для
  `snooze` — `snooze_origin` планового срока равен `origin_key`; для
  `assignment` — любое. Тогда: `Edit { resend_if_gone: false }` сообщения в
  «✅ Выполнено: <название>» (+ « · <имя>», если `actor_user_id` не
  получатель) с единственной кнопкой «🗑 Убрать»; отложенное
  `cleanup`-удаление на `completed_at + 10 минут` с ключом
  `notice-expire:{chat}:{msg}:{event_id}`; запись `closed_at`,
  `closed_reason = 'completed'` и `closed_by_event`.
- **Закрыть по назначению.** `closed_at IS NULL`, задача открыта, у неё есть
  исполнитель, и это не получатель. Тогда: `Edit { resend_if_gone: false }` в
  «👤 Назначено: <название> · <имя исполнителя>» с единственной кнопкой
  «🗑 Убрать»; отложенное `cleanup`-удаление на `now + 10 минут` с ключом
  `notice-expire:{chat}:{msg}:assigned:{now_ms}`; запись `closed_at = now`,
  `closed_reason = 'assigned'`. Копия самого исполнителя под условие не
  попадает и остаётся. Если в одном тике есть и выполнение, и назначение,
  побеждает выполнение.
- **Вернуть.** До удаления (`closed_at` + 10 минут; для выполнения —
  `completed_at` + 10 минут) причина закрытия исчезла: для `completed` —
  выполнение `closed_by_event` больше не действующее (по
  `COMPLETION_SELECTION`: отменено или снято `reopened`); для `assigned` —
  исполнителя сняли или назначили получателя. Тогда:
  `cancel_scheduled_deletes`, `Edit { resend_if_gone: false }` в обычный вид
  по виду доставки и текущему состоянию задачи (`assignment` —
  `assignment_ui`, `reminder`/`snooze` — `reminder_ui` с заголовком «⏰ Пора»;
  исходный текст «через N минут» не восстанавливается), `closed_at`,
  `closed_reason` и `closed_by_event` очищаются. Копия, закрытая по
  назначению, которую потом выполнили, остаётся закрытой и удаляется по
  своему сроку.

Сообщение «😴 Напомню …» — это сообщение исходной доставки `reminder`. Пока
отложенное напоминание не доставлено и не отменено, исходная доставка не
убрана, и при выполнении или назначении задачи другому шаг перерисует
«😴 Напомню …» в «✅ Выполнено» или «👤 Назначено».
Когда 0017 позже снимет это сообщение (отмена snooze), удаление уже
удалённого или правка удалённого (`resend_if_gone = false`) ничего не
вернут.

Своё сообщение, в котором нажали «✓ Выполнено», шаг не трогает:
`notify::complete` под `FOR UPDATE` записи доставки, чей `outbox.message_id`
равен сообщению нажатия, записывает `closed_at`, `closed_reason = 'completed'` и `closed_by_event` (id берётся
из `completions::latest_for_item` после выполнения); дальше сообщение ведёт
`show_done` из 0017. `notify::undo` под той же блокировкой очищает поля этой
доставки. Доставки сводного сообщения в кандидаты не входят.

Альтернатива — синхронно в `items::complete`. Отклонена: репозиторий не
знает о Telegram, а HTTP API и HA пришлось бы учить ставить сообщения в
outbox.

### 5. Имя выполнившего и исполнителя

Используется отображаемое имя активного участника, как в журнале выполнений.
Формат без рода и без склонения имени: «✅ Выполнено: Вынести мусор · Маша»,
«👤 Назначено: Вынести мусор · Маша». Если выполнивший исключён из household
или выполнение без участника (HA, интеграции), имя не показывается.

## Risks / Trade-offs

- [Больше сообщений: общие задачи теперь напоминают всем] → решение
  пользователя; кто не хочет — назначает исполнителя; копии закрываются
  автоматически.
- [Назначение по ошибке и сразу снятое] → копии у остальных на пару тиков
  становятся «👤 Назначено» и возвращаются, если исполнителя сняли в течение
  10 минут.
- [Отложенное напоминание человека, у которого задачу забрали, больше не
  приходит] → совпадает с правилом получателя: о чужой задаче не напоминаем.
- [Сообщение старше 48 часов не удалить] → кандидаты ограничены 47 часами;
  более старые сообщения остаются как есть. Кнопка «🗑 Убрать» у закрытой копии
  работает и после истечения токенов (0017).
- [Отмена выполнения после удаления копии] → копия не восстанавливается;
  напоминание о том же вхождении повторно не планируется (доставка `sent`).
  Окно восстановления совпадает с окном отмены, поэтому это возможно только при
  гонке на границе 10 минут.
- [Нагрузка шага на каждом тике] → выборка ограничена `status = 'sent'` и
  48 часами по частичному индексу.

## Migration Plan

- `0026_notice_closed.sql` — nullable-колонки и частичный индекс; откат —
  `DROP COLUMN`, `DROP INDEX`. Номер сдвигается, если предыдущие изменения
  слиты в другом порядке.
- После выката общие задачи начинают напоминать всем со следующего тика:
  остальным участникам сразу придут напоминания по сегодняшним общим задачам,
  которые ещё в окне доставки; уже отправленные автору не дублируются.
- Откат кода: правило получателя возвращается, колонки не читаются; поле
  `resend_if_gone` в payload старый код игнорирует (правка при `MessageGone`
  снова присылает новое сообщение).
