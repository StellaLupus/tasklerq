# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что определяет подход.

- Элемент любого списка — строка `items`; поведение ветвится по `lists.kind`
  (`tasks`, `shopping`, `checklist`). Срок — одна точка: `due_at` XOR `due_date`
  (`items_due_exclusive`).
- Движок повторений (`src/domain/recurrence.rs`) держит в строке срок текущего
  вхождения и считает следующее от него и якорной даты. Вперёд серию двигает
  только завершение задачи.
- Планировщик (`src/jobs/scheduler.rs`), сводка (`digest.rs`) и счётчики меню
  (`storage/repositories/items/stats.rs`) выбирают элементы явным условием
  `l.kind = 'tasks'` и `i.status = 'open'`.
- Календарь (`src/domain/calendar.rs`) уже отдаёт начало и исключающий конец,
  но конец дорисовывает сам: +1 день для вседневного срока, +1 час для срока со
  временем.
- Разбор собирает в контекст LLM все неархивные списки
  (`src/capture/context.rs`) и ищет целевой список по имени
  (`src/capture/validate.rs`).
- Интеграция Home Assistant живёт в соседнем репозитории `tasklerq-ha` и
  создаёт `todo` для каждого неархивного списка, не глядя на `kind`
  (`custom_components/tasklerq/todo.py`). Конец события календаря она берёт из
  ответа `GET /calendar`.
- Дальний ориентир — экспорт в календарь телефона: событие должно без потерь
  ложиться в iCalendar `VEVENT`.

## Goals / Non-Goals

**Goals:**

- Ввести событие, не меняя семантику срока, выполнения и просрочки задачи.
- Переиспользовать существующие механизмы: строку `items`, движок повторений,
  ключи вхождений, доставку уведомлений, редактор, журнал и отмену действий.
- Хранить событие так, чтобы экспорт в `VEVENT` не требовал переделки модели:
  начало и конец, стабильный идентификатор, версия.

**Non-Goals:**

- Исключения серии, кроме переноса ближайшего вхождения (таблица `EXDATE` /
  `RECURRENCE-ID`).
- Импорт чужих событий и двусторонняя синхронизация.
- Уведомление о назначении для событий.
- Напоминание о каждом дне многодневного события.

## Decisions

### 1. Событие — строка `items` в списке с kind `events`

Событие хранится в той же таблице; тип определяет список. Отдельная таблица
событий потребовала бы повторить журнал, отмену, мягкое удаление, поиск, теги,
редактор и доставку уведомлений, которые привязаны к `item_id`. Флаг «это
событие» на самой строке отвергнут: тип уже однозначно задаёт список, а второй
источник истины дал бы рассогласование.

Следствия:

- `status` события всегда `open`; `complete` и `reopen` отклоняются в
  репозитории (`items/lifecycle.rs`), чтобы запрет действовал для API, бота и
  групповых действий одинаково.
- Приоритет события всегда `normal`; подзадачи, количество и единица
  отклоняются валидацией, а не молча отбрасываются.
- Перенос между списками разрешён только внутри одного класса: событие — в
  список событий, остальное — не в список событий.

### 2. Начало — существующие `due_at` / `due_date`, конец — новые `end_at` / `end_date`

У события `due_*` означает начало. Новые колонки `end_at timestamptz` и
`end_date date` хранят конец. Так SQL планировщика, сортировки, ключи вхождений
(`jobs/keys.rs`) и перенос вхождения работают для события без изменений.

Альтернатива — отдельные `start_*` для событий — отвергнута: все выборки по
времени пришлось бы писать через `COALESCE`, а движок повторений — учить двум
полям. Цена выбранного варианта — в API начало события называется `due_at` /
`due_date`; это описывается в `docs/ha-api.md`.

Правила:

- Конец того же вида, что начало: `end_at` только при `due_at`, `end_date`
  только при `due_date`. Ограничения БД: `end_at IS NULL OR end_date IS NULL`,
  `end_at IS NULL OR (due_at IS NOT NULL AND end_at > due_at)`,
  `end_date IS NULL OR (due_date IS NOT NULL AND end_date >= due_date)`.
- `end_date` хранится включительно (последний день события) — так его вводит и
  читает человек. В календарном ответе и в будущем экспорте он превращается в
  исключающий (`end_date + 1`).
- «Конец только у событий» и «у события обязательно начало» проверяет домен:
  ограничение БД не может посмотреть в `lists.kind` без триггера.
- Длительность не больше 366 дней — тот же предел, что у интервала календаря.
- Хранится конец, а не длительность: `VEVENT` допускает оба варианта, но конец
  читается и правится напрямую, а «сдвиг начала сохраняет длительность»
  реализуется одной операцией в `items/write.rs`.

### 3. Эффективный конец

Одна функция домена возвращает момент, после которого событие считается
прошедшим:

- задан `end_at` — он;
- задан `end_date` — начало следующего за ним дня в часовом поясе household;
- только `due_at` — `due_at + 1 час`;
- только `due_date` — начало следующего дня в часовом поясе household.

Значения по умолчанию (1 час, 1 день) совпадают с тем, что календарь рисует
сейчас. На эту функцию опираются: прошедшее событие, автопереход, скрытие из
повестки, счётчик «на сегодня» и отмена устаревших напоминаний. Вседневные границы считаются в поясе household, а не пользователя,
чтобы событие проходило для всех участников одновременно.

### 4. Автопереход — отдельный шаг тика планировщика

Новый шаг тика выбирает события с правилом повторения, у которых эффективный
конец не позже `now`, и для каждого:

1. находит через `Recurrence::next_after` первое вхождение, эффективный конец
   которого позже `now` (после простоя пропущенные вхождения перешагиваются
   сразу);
2. записывает его начало в `due_*`, сдвигает конец на ту же длительность,
   сбрасывает слот перенесённого вхождения (`occurrence_date`), увеличивает
   `version`;
3. если следующего вхождения нет, строку не меняет — событие остаётся прошедшим.

Запись в журнал выполнений не создаётся, запись в журнал событий — тоже: это
не действие пользователя, и отменять его нечем. Шаг выполняется независимо от
остальных шагов тика, как они устроены сейчас; ошибка на одном событии не
прерывает обработку остальных. Строка берётся `FOR UPDATE SKIP LOCKED`, чтобы
не столкнуться с правкой пользователя.

Увеличение версии нужно, чтобы открытый редактор и устаревшие кнопки
обнаружили смену вхождения. Напоминания и snooze привязаны к ключу вхождения,
поэтому старые отменяются существующим правилом актуальности, а новое
планируется по новому сроку.

Альтернатива — считать вхождения на лету и хранить исключения отдельной
таблицей — отвергнута на этот change: планировщик и все выборки по сроку
пришлось бы писать для событий заново. Перейти к ней позже можно добавлением
таблицы исключений; хранимое начало серии при этом восстанавливается из
`recurrence_anchor_date`.

### 5. Повторение события

Проверка «повторение только у задач» (`domain/validation.rs`,
`items/write.rs`) расширяется на списки событий. Развёртка
`Recurrence::occurrences_between` возвращает начала; календарь добавляет к
каждому длительность события. Чтобы многодневное вхождение, начавшееся до
интервала запроса, попало в ответ, развёртка для событий запрашивается с
началом, сдвинутым назад на длительность.

### 6. Календарные вхождения и повестка — одна развёртка

`CalendarEvent` получает тип элемента и настоящий конец. Повестка в боте
строится той же функцией развёртки по окну в семь дней, затем отбрасывает
выполненные задачи и прошедшие вхождения событий и раскладывает многодневные
события по дням. Отдельная выборка для повестки отвергнута: повторяющиеся
элементы пришлось бы разворачивать вторым способом, и повестка разошлась бы с
календарём Home Assistant.

Экран — `Screen::Agenda { list: Option<Uuid>, page }`: без списка это общая
повестка, со списком — повестка одного списка событий, открываемая из «Все
списки». Раздел «Просрочено» на первой странице берёт открытые задачи со
сроком раньше текущего момента отдельным запросом, потому что календарная
развёртка не возвращает прошлое.

### 7. Редактор и карточка

Редактор элемента получает шаги «Конец» и ввод конца текстом; состав полей
определяется типом списка, как сейчас для покупок. Ввод одного времени в поле
«Конец» относится к дню начала, а если оно не позже времени начала — к
следующему дню; это правило живёт в форме, а не в домене, потому что API
всегда получает полный момент времени. «📅 Перенести» в карточке события —
существующий экран быстрого срока без варианта «Без срока».

### 8. Уведомления

- Планирование напоминаний и сбор сводки включают `kind = 'events'`.
  Напоминание многодневного события планируется только на день начала —
  существующая выборка по `due_date` это и даёт.
- Правило актуальности (`jobs/notice.rs`) для события дополняется условием
  «эффективный конец уже прошёл»: так не приходит напоминание, которое тихие
  часы вынесли за конец события.
- «Закрыть» — новое действие без состояния: удаляет сообщение через
  существующий `Outgoing::Delete`. Запись доставки не меняется, поэтому
  напоминание о том же вхождении не планируется повторно.
- Snooze у события нет. «📅 Перенести» в напоминании открывает тот же экран
  быстрого срока, что карточка события: пользователь меняет само событие, а
  напоминание о новом начале планируется обычным путём по новому ключу
  вхождения. Отложить напоминание, не трогая событие, отвергнуто: напоминание
  после начала события бесполезно, а условный показ кнопок усложнял бы и
  отрисовку, и правило актуальности.
- В сводном сообщении после тихих часов блок события рисуется с «📅 Перенести»
  и «Открыть»; «✓ Выполнить все» и «Отложить все на час» пропускают события на
  уровне выборки, а не полагаются на отказ действия.

### 9. Списки событий

Список «Календарь» создаётся рядом с «Задачи» и «Покупки» при создании
household и миграцией — существующим household. `POST /lists` принимает kind
`events` наравне с `shopping` и `checklist`. Существующие ограничения — один
список по умолчанию на kind, запрет архивировать список по умолчанию, лимит 20
списков — действуют без изменений. Если у household уже 20 списков, миграция
всё равно создаёт «Календарь»: лимит проверяется при создании пользователем, а
не ограничением БД.

### 10. Разбор не видит события

Списки событий исключаются при сборе контекста разбора. Этого достаточно и
для промпта, и для выбора целевого списка: обе стороны берут списки из одного
контекста. Правка промпта capture-v3 не нужна; события в разборе появятся
вместе с capture-v4.

### 11. Home Assistant

В этом репозитории меняется только контракт API. В `tasklerq-ha` — пропуск
списков с kind `events` при создании `todo`-сущностей и обновление копий
документов. Календарная сущность изменений не требует: она берёт границы из
ответа календаря.

## Risks / Trade-offs

- [Старая версия `tasklerq-ha` создаст `todo` для списка «Календарь», а
  отметка «выполнено» вернёт `422`] → задача на обновление интеграции входит в
  change; до её выпуска поведение описано в `docs/home-assistant.md`.
- [Автопереход увеличивает версию события, пока пользователь правит его в
  редакторе] → сохранение даст существующий экран конфликта версий; для события
  длиной в час это редкий случай.
- [`due_*` в API означает срок у задачи и начало у события] → описано в
  `docs/ha-api.md` и `docs/domain-model.md`; переименование было бы
  несовместимым изменением ради единообразия.
- [Прошедшие разовые события копятся без срока хранения] → объём мал; правило
  хранения можно добавить отдельно, когда появится экспорт.
- [Повестка разворачивает все элементы household на каждое открытие экрана] →
  окно ограничено семью днями, развёртка — существующими пределами календаря;
  экран ограничен 30 строками.
- [У household с двумя списками по умолчанию после миграции их три, и порог
  кнопки «Все списки» сработал бы у всех] → порог считает списки без событий.
- [Напоминание о вседневном событии привязано к поясу получателя, а конец дня
  события — к поясу household] → расхождение возможно только у участников в
  разных поясах и не больше чем на разницу поясов.

## Migration Plan

1. Миграция `0016`: `ALTER TYPE list_kind ADD VALUE 'events'`. Отдельным файлом:
   PostgreSQL не разрешает использовать новое значение enum в транзакции, где
   оно добавлено, а каждая миграция выполняется в своей транзакции.
2. Миграция `0017`: колонки `end_at`, `end_date` с ограничениями; список
   «Календарь» (`kind = 'events'`, `is_default`) каждому неудалённому household,
   у которого его нет. Номер `0015` занят миграцией `0010-search-index`,
   которая выполняется раньше; если к началу работ заняты и эти номера, берутся
   следующие свободные.
3. Развёртывание сервера, затем обновление `tasklerq-ha`.

Откат: предыдущая версия сервера не читает значение `events` в `list_kind`,
поэтому откат кода требует восстановления базы из резервной копии, сделанной
перед миграцией. Это записывается в `docs/deployment.md`.

## Open Questions

- Нужна ли в повестке кнопка быстрого создания задачи со сроком рядом с
  «➕ Событие». Решается по опыту использования; на модель и спеки не влияет.
