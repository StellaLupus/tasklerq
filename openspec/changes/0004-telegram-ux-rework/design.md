# Design

## Context

Мотивация — в proposal.md (раздел Why). Требования — в дельтах
`telegram-rich-ui`, `llm-capture`, `notifications-reminders` и
`task-management`.

Как устроено сейчас:

- **Экраны.** `Screen` и `Action` (`src/telegram/bot/model.rs`)
  сериализуются в JSON. Экран хранится в `telegram_views.state`, действие — в
  `callback_tokens`. Если состояние не разбирается, `Ctx::refresh` показывает
  меню (`unwrap_or(Screen::Menu)`).
- **Баннер** — одна строка `Ctx::banner`. Она рисуется жирным абзацем над
  экраном при ближайшей отрисовке и нигде не хранится.
- **Формы.** Создание (`ItemForm`) идёт мастером по `forms/state.rs:advance`.
  Правка (`EditForm`) сохраняет каждое поле сразу через `apply_patch`. Правка
  пункта черновика LLM — отдельный путь `capture::edit`.
- **Строки списков.** Задачи — `[☐][название]`, покупки — `[☐ название][⋯]`.
  Кнопки одного ряда Telegram делает одинаковой ширины.
- **Выполнение.** `items::complete` пишет событие `completed` с
  `payload = {before, after}` — полными снимками `Item`. У повторяющейся
  задачи статус остаётся `open`, а срок переносится. `reopen` событие
  выполнения с собой не связывает (`undo_of = NULL`) и для повторяющейся
  задачи ничего не делает: она всегда `open`. `undo_last` связывает
  компенсирующее событие через `undo_of`.
- **Смена срока.** `items::update` при смене срока у повторяющейся задачи
  переписывает `anchor_date` (`items/write.rs:227`). Расчёт `next_after`
  идёт от `anchor_occurrence()` и берёт первое вхождение строго позже
  текущего срока и момента завершения.
- **Разбор.** `capture::intake` ставит задание `capture_jobs` с JSON
  `payload`. `capture_worker` создаёт черновик `capture_drafts` (`raw_text` не
  длиннее 2000 символов) и показывает его через `present_to` на активном
  экране чата.
- **События.** `item_events` хранится `RETENTION_EVENTS_DAYS` (365 дней).
  Индексы — `(item_id, created_at)`, `(household_id, created_at)` и
  `undo_of`. Внешний ключ `item_id` стоит `ON DELETE CASCADE`.

## Goals / Non-Goals

**Goals:**

- Один редактор элемента для создания, правки и пункта черновика.
- Одна модель строки списка и одна модель навигации на всех экранах.
- Журнал выполнений без новой таблицы — из существующих событий.
- Выкатывать по этапам: каждый этап сам по себе оставляет бот рабочим.

**Non-Goals:**

- Менять HTTP API: `PATCH` срока по-прежнему сдвигает серию; перенос
  вхождения есть только в боте. Исключение — аддитивное поле
  `recurrence.occurrence_date` и `recurrence.occurrence_time` в ответе только
  для чтения (решение 6).
- Фильтры и сортировка списков, журнал одного списка, экспорт журнала.
- Переписывать уведомления сверх подписей кнопок.
- Менять правило видимости якоря и outbox из 0003.

## Decisions

### 1. Этапы и ветки

Работа идёт этапами 0 → A → B → C → D. У каждого этапа своя ветка от `main` и
свой PR. Этап 0 ручной: прогон на `@tasklerqtestbot`, результат записывается
в `docs/telegram-ux.md` §14. Если этап 0 опровергнет допущение, правится
раскладка этапа A: например, если ряд из трёх кнопок обрезается — в редакторе
ряды по две. Спеки при этом не меняются.

Change архивируется после этапа D.

### 2. Строка списка и режим правки покупок

`Screen::List` получает поле `edit: bool` с `#[serde(default)]`, поэтому
старое состояние читается как обычный режим.

- В списках задач строка ведёт `Action::Go { Screen::Item }`.
- В покупках строка ведёт `Complete`/`Reopen`, а при `edit = true` —
  `Go { Item }`.
- Статус показывается в подписи: у покупок `☐`/`☑` перед названием плюс
  раздел «Купить»/«Куплено», у задач `✅` в разделе «Выполнено сегодня».
  Открытая задача отметки не несёт: её статус задаёт раздел срока.

Отвергнуто: оставить `☐` отдельной кнопкой со свёрнутой подписью. Ширина у
кнопок одинаковая, сжатия подписи RichMessage не даёт.

### 3. Баннер с кнопками вместо экрана `Completed`

`Ctx::banner` становится `Banner { text, buttons: Vec<Button<Action>> }`. Это
по-прежнему эфемерный блок над экраном, в `telegram_views` он не хранится.

После «✓ Выполнено» бот делает `present(back)` с баннером «✅ Выполнено: …» и
кнопкой `Action::Undo`. Тот же механизм используют:

- баннер прямого добавления покупок с «↩️ Отменить»;
- баннер выбора дубликата;
- баннер «Черновик готов [Открыть]»;
- баннер «Срок: завтра, 18:00» после быстрого срока.

`Screen::Completed` удаляется. Сохранённое состояние с ним не разбирается, и
`refresh` показывает меню, как уже бывает с битым состоянием.

Отвергнуто: хранить баннер в `telegram_views`. Баннер — ответ на только что
сделанное действие. Если бы он переживал перерисовку, он висел бы над
экранами, к которым не относится. Потерянную отмену заменяют «↩️ Вернуть» в
карточке и раздел «Выполнено сегодня».

### 4. Выполнения: один источник для «Выполнено сегодня», журнала и карточки

В `storage::repositories::items` появляется модуль `completions`. Выполнение
— это событие `completed`, для которого нет компенсирующего события:

- нет события с `undo_of = id`;
- для задачи без повторения — нет события `reopened` того же элемента после
  этого выполнения и до следующего `completed`. Это правило покрывает и
  старые возвраты, которые писались без `undo_of`.

Выполнения удалённых задач (`items.deleted_at IS NOT NULL`) отбрасываются.

Поля берутся из снимка `payload.before`, но не через разбор целого `Item`:
читаются только `title`, `due_at`, `due_date` и `list_id`, ошибки разбора
отдельного поля терпимы. Кто выполнил — `actor_user_id` события, время —
`created_at`.

Пропавшее название показывается как «Без названия», а запись остаётся.
Отвергнуто: разбирать `Item` целиком, как делает `reopen`. Тогда любое
изменение структуры `Item` молча стирает историю.

Выборки:

- **«Выполнено сегодня» списка** — события household с `created_at` от
  начала дня в поясе пользователя (индекс `household_id, created_at`),
  фильтр по `before.list_id` в коде. За день событий мало.
- **Журнал** — события `completed` household за срок хранения, сортировка по
  плановой дате, вычисленной в SQL из `before.due_at` (в поясе household) или
  `before.due_date`. Порядок: от поздних к ранним, затем «без срока» по
  факту, затем `id`. Пагинация `LIMIT/OFFSET` по 8. Индекса по выражению
  нет: при 5–10 выполнениях в день за год это тысячи строк одного household,
  полный проход по ним дешёвый. Если станет дорого, путь известен —
  денормализованные колонки.
- **Блок «Выполнения» в карточке** — последние пять выполнений элемента по
  индексу `(item_id, created_at)`.

### 5. Возврат выполнения

Новая доменная операция `items::revert_completion(item_id, completion_id)`.

- Возвращать можно только последнее неотменённое выполнение элемента.
- У задачи без повторения это прежний `reopen`.
- У повторяющейся задачи возврат допустим, если `items.version` равна версии
  из `payload.after` этого выполнения, то есть задача не менялась после него.
  Тогда восстанавливаются `due_at`/`due_date`, `recurrence.occurrence_date`,
  `recurrence.occurrence_time`, `completed_at` и `completed_by_user_id` из `payload.before`.
- Событие `reopened` пишется с `undo_of = completion_id`, поэтому журнал
  перестаёт показывать это выполнение по общему правилу из решения 4.

Кнопки «↩️ Вернуть» в карточке выполненной задачи и в разделе «Выполнено
сегодня» ведут сюда же. `undo_last` с окном 10 минут остаётся для «↩️
Отменить» в баннере.

### 6. Перенос текущего вхождения

Новая доменная операция `items::reschedule_occurrence(item_id, version, due)`.
Она меняет `due_at`/`due_date`, увеличивает `version` и пишет событие
`updated`, но `recurrence_anchor_date` не трогает. У задачи без повторения
она эквивалентна `update` с одним полем срока.

Два пути смены срока у повторяющейся задачи различаются намеренно:

- поле «Срок» в редакторе — `items::update`: меняет серию, якорь и время
  суток следующих вхождений (день недели еженедельной серии задаёт правило);
- быстрый срок в карточке («📅 Срок», включая «📅 Дата и время») —
  `reschedule_occurrence`: меняет только текущее вхождение, следующие идут по
  правилу со своим временем.

**Слот вхождения.** Из срока, якоря и правила нельзя понять, какую дату
правила занимает перенесённое вхождение. Пример: по вторникам срок 6 ноября
получается и из просроченного 3-го («Сегодня» в пятницу), и из 10-го
(«Сегодня» заранее). Следующий срок в первом случае 10-е, во втором 17-е.
Поэтому `Recurrence` получает поле `occurrence_date: Option<NaiveDate>`
(колонка `items.recurrence_occurrence_date`, `serde(default)`):

- `None` — срок стоит на своей дате правила.
- `reschedule_occurrence` записывает `coalesce(occurrence_date, дата текущего
  срока)`. Повторный перенос слот не меняет. Если новый срок равен исходному
  сроку вхождения (та же дата и то же время суток или та же вседневность),
  слот обнуляется. Попадание на другую дату правила слот не обнуляет.
- Выполнение, `update` срока или правила (бот и HTTP `PATCH`) слот обнуляют.
- `next_after` берёт первое вхождение строго позже `max(срок, слот,
  завершение)`.
- Календарь (`expand_item`) скрывает вхождения правила не позже `max(срок,
  слот)` и показывает текущее вхождение на сроке.

**Время серии.** Время суток серии хранится только в текущем сроке
(`due_at`), поэтому перенос на другое время («📅 Дата и время» → «чт 12:00»)
или во вседневный срок без памяти о нём переносил бы время на все следующие
вхождения. Поэтому слот хранит и время: `occurrence_time: Option<NaiveTime>`
(колонка `items.recurrence_occurrence_time`, локальное время в
`recurrence.timezone`, `serde(default)`):

- `reschedule_occurrence` при пустом слоте записывает вместе с датой время
  текущего срока: локальное время для срока со временем, `None` для
  вседневного. Повторный перенос время слота не меняет.
- Время задано только вместе с датой слота; без слота поле `None`, его
  обнуляют те же операции, что и дату.
- Если слот задан, следующее вхождение после выполнения (`next_after`) и
  следующие вхождения в календаре получают время и тип срока из слота:
  `occurrence_time` → срок со временем, `None` → вседневный. Без слота —
  как раньше, из текущего срока.

Пример: «каждый вторник 9:00», вхождение 10 ноября перенесено на четверг
12 ноября 12:00 и выполнено — следующий срок вторник 17 ноября 9:00. Если в
редакторе поменять срок на 15:00, меняется серия: следующие вхождения в
15:00.

Поля лежат в `Recurrence`, поэтому попадают в снимки `payload.before/after`,
и `undo_last`, `reopen` и `revert_completion` восстанавливают их без
отдельного кода. Цена — поля видны в ответе HTTP API. `RecurrenceInput` их не
принимает.

Напоминания перепланируются тем же путём, что и при `update`: планировщик
смотрит на текущий `due_at`.

Отвергнуто:

- Флаг «не переякоривать» в общем `ItemPatch`. Он открыл бы поведение в HTTP
  API, а это вне цели изменения.
- Выводить слот как ближайшую дату правила не раньше срока. Это ломает
  перенос просроченного вхождения на сегодня: пропадает неделя.
- Искать слот в журнале событий. Связывает домен с аудитом и с его сроком
  хранения.
- Отдельная колонка вне `Recurrence`. API не меняется, но снимки, undo и
  возврат пришлось бы учить отдельно.

### 7. Единый редактор

`ItemForm` и `EditForm` заменяет одно состояние `Editor` в
`conversation_states`:

```text
Editor {
  target: New { list_id, kind } | Item { item_id, base: ItemSnapshot }
        | DraftItem { draft_id, index },
  draft: ItemDraft,          // текущие значения полей
  touched: BTreeSet<Field>,  // что пользователь менял
  field: Option<Field>,      // открытый экран поля; None — сам редактор
  error: Option<String>,
}
```

- **Экран поля** после выбора или ввода ставит `field = None` и добавляет
  поле в `touched`.
- **Мультивыбор** (теги, подзадачи, дни недели) закрывается «Применить».
- **Повторение** — один экран: частота, дни недели, правило месяца, интервал.
- **«💾 Сохранить»:**
  - `New` — валидация и `items::create`. Для покупки проверяется дубликат,
    экран выбора остаётся прежним.
  - `Item` — перечитать задачу. Для каждого поля из `touched` сравнить
    текущее значение с `base`. Если и текущее, и наше значение отличаются от
    `base` и не совпадают между собой, это конфликт: экран с обоими
    значениями и кнопками «Оставить мой» и «Оставить текущий». Иначе
    `items::update` с патчем только по `touched` и текущей `version`. Теги и
    подзадачи сравниваются как поле целиком. Повторение сравнивается без
    `occurrence_date` и `occurrence_time`: перенос вхождения другим участником не конфликтует с
    правкой правила.
  - `DraftItem` — записать пункт в черновик и перепроверить его; бот
    возвращается к карточке черновика.
- **Создание из меню** открывает поле «Название», затем редактор со списком
  задач по умолчанию. Кнопка «📋 Список» переключает тип, как в нынешней
  быстрой форме. Из экрана списка тип и список уже известны.
- **Старое состояние** `conversation_states` с прежними формами не
  разбирается в `Editor`. Оно трактуется как истёкшее, и бот показывает
  «правка устарела».

### 8. Навигация и хлебные крошки

Глубина экрана определяется цепочкой `back`, которая уже есть у
`Screen::Item`, и статически для остальных экранов (`Screen::depth()`).

- Общий хелпер `nav_row(screen)` всегда ставит «⬅️ Назад», а при глубине
  больше двух ещё «🏠 Меню».
- Хлебные крошки — `Screen::trail()`: короткие имена родителей («Задачи»,
  «Настройки») и название текущего экрана, обрезанные до 60 символов.
- Подписи «В меню», «К списку», «Отмена» как возврат убираются.

### 9. Маршрутизация текста

`handle_text` при отсутствии формы читает активный экран из
`telegram_views.state` и выбирает путь:

| Экран | Путь |
| --- | --- |
| `Editor`, поле ждёт текст | значение поля (как сейчас) |
| `Editor`, поле не ждёт текст | баннер «Сначала сохраните или отмените правку» |
| поиск, `Results` | новый поиск |
| `List` покупок | прямое добавление (решение 10) |
| `List` задач | разбор с `default_list_id` в `payload` задания |
| остальные | общий разбор |

Подсказка ввода строится той же таблицей, чтобы подсказка и поведение не
разошлись.

### 10. Прямое добавление покупок

- **С разбором.** `intake` ставит задание с
  `payload.target = { list_id, direct: true }` и перерисовывает список с
  баннером «Добавляю…». `capture_worker` разбирает текст с этим списком как
  целевым. Дальше в одной транзакции:
  - позиции покупок без дубликата создаются через `items::create`;
  - дубликаты откладываются;
  - элементы другого типа уходят в черновик по правилу дописывания
    (решение 11).
- **Без разбора** (LLM выключен или недоступен) текст делится в боте по
  запятым и переводам строк, без задания. Каждая часть — позиция с
  количеством 1.
- **Показ результата.** Если активный экран всё ещё этот список, он
  перерисовывается с баннером. Иначе баннер «Добавлено в «Покупки»: …»
  ставится на текущий экран, по правилу позднего результата.
- **Отмена** — `Action::AddedUndo { item_ids }`: мягкое удаление созданных
  позиций в окне 10 минут, с проверкой автора, как у `Cleared`.
- **Дубликат.** Кнопки выбора — `Action::DuplicateIncrease { item_id,
  version, quantity }` и `Action::DuplicateSeparate { list_id, title,
  quantity, unit }`. Данные лежат в действии токена, отдельное хранение не
  нужно.

Лимит 10 разборов в минуту действует как обычно.

### 11. Дописывание в черновик и поздний результат

Миграция `capture_draft_parts` (следующий свободный номер):
`capture_drafts.raw_parts text[] NOT NULL DEFAULT '{}'`. `raw_text` остаётся склейкой частей через перевод строки,
поэтому существующие читатели и ограничение в 2000 символов работают как
есть. Retention очищает `raw_parts` вместе с `raw_text`.

`capture_worker` по готовому разбору из Telegram:

1. Берёт `FOR UPDATE` последний ожидающий черновик того же чата и
   пользователя.
2. Если он есть и сумма не больше 20 элементов и 2000 символов — дописывает
   пункты, `raw_parts`, `raw_text` и продлевает `expires_at = now + 15 мин`.
3. Иначе создаёт новый черновик.

Блокировка строки упорядочивает два одновременно завершившихся разбора.

Показ результата: если активный экран — `Processing { job_id }` этого задания
или `Draft` этого черновика, то `present_to(Draft)`. Иначе экран не
меняется, на нём баннер «Черновик готов [Открыть]».

Главное меню показывает строку «📝 Ждёт подтверждения» по самому свежему
ожидающему черновику пользователя.

Отвергнуто: каждый черновик отдельным сообщением. Это ломает «одно сообщение
— один экран» и засыпает якорь.

### 12. Настройки

Новые экраны:

- `Screen::Profile` — имя и часовой пояс;
- `Screen::Danger` — удаление пространства для владельца, выход для
  участника;
- `Screen::LeadTime` — 5/15/30/60 минут и «Своё…».

`Screen::Timezones` открывается из «Профиля». Экран уведомлений собирается
блоками через `rule()`. Переключатель подписывается действием («Выкл» при
включённом). Права на действия не меняются, меняется только их
расположение.

### 13. Подписи

Строки интерфейса собираются в `src/telegram/ru.rs`:

| Действие | Подпись |
| --- | --- |
| статус задачи | `DONE_BUTTON = "✓ Выполнено"` |
| статус покупки | `BOUGHT_BUTTON = "✓ Куплено"` |
| групповое действие | `DONE_ALL_BUTTON = "✓ Выполнить все"` |
| закрыть мультивыбор | `APPLY_BUTTON = "Применить"` |

Golden-тест экранов проверяет, что подписи кнопок не содержат «Готово».

## Risks / Trade-offs

- **Отмена в баннере теряется при перерисовке.** Например, пришло
  уведомление, и якорь засыпан. → Для задач остаются «↩️ Вернуть» в карточке и
  раздел «Выполнено сегодня». Для прямого добавления покупок — ручное
  удаление позиции. Принимаем.
- **Прямое добавление сохраняет ошибку разбора без подтверждения.** → Окно
  отмены 10 минут. LLM по-прежнему только создаёт элементы и не меняет
  существующие. Дубликаты ждут выбора, как требует `shopping-lists`.
- **Слияние полей в редакторе сложнее «последний пишет всё».** → Конфликт
  проверяется только по `touched`. Списки (теги, подзадачи) сравниваются
  целиком. Тесты на оба сценария дельты.
- **Журнал сортирует по выражению над JSON без индекса.** → На масштабе семьи
  это тысячи строк. Метрика длительности запроса уже есть в пуле. Решение 4
  оставляет путь к денормализации.
- **Откат образа этапа B оставляет устаревший слот.** Старый код поля не
  видит и не обнуляет, а CHECK `items_recurrence_shape` требует пустой слот
  без правила: старый `update` с «Не повторять» у задачи со слотом получит
  ошибку БД. → Сразу при откате образа выполнить
  `UPDATE items SET recurrence_occurrence_date = NULL,
  recurrence_occurrence_time = NULL`.
- **Старые снимки `payload.before` могут не содержать нужного поля.** →
  Терпимый разбор, запись не теряется.
- **Раздел «Выполнено сегодня» последний и на длинном списке уходит на
  дальние страницы.** → Счётчик в шапке на каждой странице.
- **Пользователь привык к старой раскладке.** → Обновить `/help`. Этапы
  выкатываются по очереди, а не одним скачком.
- **Старые кнопки и состояния после выкатки.** Токены с удалёнными действиями
  и `telegram_views` с `Completed`/`Add`. → Неразбираемое действие
  обрабатывается как устаревшая кнопка, неразбираемый экран — как меню. Это
  проверяется тестами на JSON старого формата.

## Migration Plan

1. Этап 0 — ручная проверка, без выкатки.
2. Этапы A и B выкатываются сменой тега образа. Этап A схему БД не меняет.
   Этап B добавляет аддитивные колонки `items.recurrence_occurrence_date` и
   `items.recurrence_occurrence_time` (одна миграция, следующий свободный
   номер). Откат — прежний тег; порядок
   повторной выкатки после отката — в Risks. Новые поля `Screen` с
   `serde(default)` старый код не читает и показывает меню.
3. Этап C добавляет миграцию `capture_draft_parts` со следующим свободным
   номером после этапа B и 0005 (аддитивная колонка). Откат образа
   безопасен: старый код колонку не видит. Дописанные черновики старый код
   показывает по `raw_text`, то есть одной цитатой.
4. Этап D схему не меняет.
5. После каждого этапа — ручной сценарий на NAS из `tasks.md`.
