# Design

## Context

- Экраны бота — RichMessage с inline-кнопками (`send_rich_message`), обычные
  сообщения — `send_message` без `reply_markup`. Reply-клавиатуры в боте нет.
  Telegram допускает в одном сообщении только один вид `reply_markup`, поэтому
  клавиатура не может жить на экране навигации.
- Все исходящие идут через outbox в порядке `seq` внутри чата
  (`src/telegram/outbox.rs`). Уже есть отложенные строки (`enqueue_at`) и
  постановка удаления в транзакции отметки доставки (`delete_after`).
  `MessageUndeletable` для удаления обрабатывается как завершённое.
- `/start` и `/menu` ставят `Placement::Fresh` (`src/telegram/bot/mod.rs`,
  `on_command`): экран всегда новым сообщением и удаление прежнего активного.
  Строка `telegram_views` для чата создаётся при обработке (`views::set`) раньше
  доставки.
- Обработанный текст пользователя удаляется общим механизмом с ключом
  `delete_dedupe_key`.
- Пользователь подтвердил: удаление сообщения, к которому прикреплена
  reply-клавиатура, убирает клавиатуру.

## Goals / Non-Goals

**Goals:**
- Один защищённый носитель на чат; после замены клавиатура видна.
- Нажатие кнопки идёт по тому же пути, что `/menu`.

**Non-Goals:**
- Рассылка клавиатуры уже зарегистрированным пользователям без их действия.
- Команды бота через `setMyCommands` и кнопка меню Telegram рядом с полем ввода.
- Другие кнопки в reply-клавиатуре (кнопку «☀️ Сводка» добавляет 0019).

## Decisions

### 1. Новый вид исходящего: `Outgoing::Keyboard { html, rows }`

Отдельный вариант, а не флаг у `Outgoing::Message`: у носителя своя логика
после доставки (запомнить `message_id`, удалить прежний) и своя защита.
Отправка — `sendMessage` с `reply_markup = {keyboard: [[{text: "🏠 Меню"}]],
is_persistent: true, resize_keyboard: true}`. В `TelegramApi` добавляется
метод `send_keyboard_message(chat_id, html, rows)`, где `rows` — раскладка
кнопок по строкам (здесь одна строка с одной кнопкой). Раскладку строит одна
функция бота `keyboard_rows()` при постановке носителя, а `rows` хранится в
payload строки outbox: доставка не зависит от слоя бота, следующие кнопки
добавляются без смены API. Подпись кнопки — существующая константа
`ru::MENU_BUTTON` («🏠 Меню»), та же, что у inline-кнопки глубоких экранов. Фейк
в тестах записывает вызов отдельным видом `Call`.

Альтернатива — прикреплять клавиатуру к `/help` или к баннеру. Отклонена: эти
сообщения не всегда отправляются и не всегда живут долго.

### 2. `message_id` носителя — колонка `telegram_views.keyboard_message_id`

Миграция `0024_telegram_keyboard.sql`: `ALTER TABLE telegram_views ADD COLUMN
keyboard_message_id bigint` и `ALTER TYPE outbox_kind ADD VALUE 'keyboard'`
для нового вида строки outbox (как `delete` в `0011`). Id носителя
записывается UPSERT-ом по `chat_id`, как `views::set_message`: обычно строка
вида уже есть (носитель ставится в том же обработчике, что и экран), но если
её нет, носитель не теряется для следующей замены.

Доставка at-least-once: если Telegram принял носитель, а транзакция отметки не
зафиксировалась, повтор пришлёт второй носитель, а id первого нигде не
останется. Такой лишний носитель допустим (spec) и в историю уходит как
обычное сообщение.

Альтернатива — отдельная таблица. Отклонена: одна строка на чат уже есть, у
неё тот же жизненный цикл.

### 3. Замена прежнего носителя — при доставке, порядок выбирает спайк

Прежний id в обоих вариантах читается в момент доставки нового носителя, а не
при постановке, поэтому два `/menu` подряд не оставят лишний носитель. Носитель
старше 48 часов даёт `MessageUndeletable`, что уже считается выполненным
удалением.

**Вариант A — сначала новый, затем удаление прежнего (по умолчанию).** В
транзакции отметки `sent` для `Keyboard`:

```
old := SELECT keyboard_message_id FROM telegram_views WHERE chat_id = $1 FOR UPDATE
UPDATE telegram_views SET keyboard_message_id = <new>
IF old IS NOT NULL AND old <> new:
    enqueue Delete{old} с ключом "keyboard:{chat_id}:{old}"
```

Момента без клавиатуры нет. Риск — клиент снимет клавиатуру при удалении
прежнего носителя, хотя новый уже поставил свою.

**Вариант B — сначала удаление прежнего, затем новый.** Доставка `Keyboard`
сама удаляет прежний носитель перед отправкой:

```
old := SELECT keyboard_message_id ... FOR UPDATE
IF old IS NOT NULL: deleteMessage(old)        -- MessageUndeletable / не найдено = ок
UPDATE telegram_views SET keyboard_message_id = NULL
new := sendMessage(...)
UPDATE telegram_views SET keyboard_message_id = <new>
```

Если отправка упала после удаления, повтор outbox уже не видит прежний id и
просто отправляет новый. Риск — мигание клавиатуры и короткое окно без неё.

**Выбор.** Задача-спайк проверяет оба порядка на живом клиенте (Telegram Web и
Android). Если при A клавиатура остаётся — берём A. Если при A клавиатура
пропадает — берём B: мигание терпимо, пропавшая кнопка — нет. Результат
спайка и выбранный вариант записываются в этот раздел до задач 2.3–2.4.

Доставка носителя, как и `Outgoing::Message`, помечает активный экран
засыпанным (`mark_buried`): носитель всегда идёт с `Placement::Fresh`, так что
на поведение это не влияет, но признак остаётся честным.

### 4. Защита носителя — проверка в доставке `Delete`

Пути удаления структурно не указывают на носитель: замена якоря удаляет
`telegram_views.message_id`, «Закрыть» удаляет сообщение с кнопкой (у носителя
inline-кнопок нет), удаление входящих касается сообщений пользователя. Как
страховка, доставка `Outgoing::Delete` пропускает (`skipped`) удаление, если
`message_id` равен текущему `keyboard_message_id` чата. Удаление прежнего
носителя под это правило не попадает: в варианте A к моменту его доставки
текущим уже стал новый, в варианте B прежний удаляется самой доставкой
`Keyboard`, а не строкой `Delete`.

### 5. Перехват текста кнопки — рядом с командами

В `on_text` до `parse_command` и до разбора форм: если `text.trim()` точно
равен `ru::MENU_BUTTON` («🏠 Меню»), вызвать общий путь меню без
носителя. Ветка `"menu"` из `on_command` выносится в функцию
`open_menu(ctx, carrier: bool)`: `/menu` → `carrier = true`, кнопка →
`carrier = false`. Обе ставят `Placement::Fresh` и очищают форму. Удаление
текста кнопки идёт общим механизмом удаления обработанных сообщений.

Совпадение требуется точное, с эмодзи: «Меню» без эмодзи остаётся обычным
текстом.

### 6. Где ставится носитель — флаг в `Ctx`, носитель перед первым экраном участника

Экран меню показывают десяток мест (`onboarding.rs` — после `claim`,
`accept_invite`, повторного `/start`; `forms::start_onboarding`;
`menu_or_onboarding`), а создание household заканчивается `Screen::Welcome`, а
не меню. Поэтому точки входа не вызывают отправку сами, а выставляют флаг:

- `/start`, `/menu` и завершение онбординга (создание household, вступление по
  приглашению, `claim`) ставят `ctx.carrier_pending = true`;
- `Ctx::present` (единая точка показа экрана), если флаг стоит, экран —
  `Screen::Menu` или `Screen::Welcome`, а `ctx.user` есть, сначала ставит
  `Outgoing::Keyboard`, принудительно переводит размещение в
  `Placement::Fresh` и сбрасывает флаг;
- экраны онбординга (пользователь ещё не участник) флаг не сбрасывают и
  носитель не ставят.

Принудительный `Fresh` нужен для онбординга, завершённого inline-кнопкой
(выбор часового пояса — callback на якоре с `InPlace`): иначе приветствие
правилось бы на месте выше носителя. Нажатие кнопки «🏠 Меню» флаг не ставит.

## Risks / Trade-offs

- [Вариант A: клиент может убрать клавиатуру при удалении *прежнего*
  носителя, хотя новый уже поставил свою] → спайк до основной реализации; при
  подтверждении — вариант B (решение 3).
- [Вариант B: мигание клавиатуры и короткое окно без неё; окно растягивается,
  если отправка нового носителя задержалась] → спайк оценивает мигание; окно
  закрывают повторы outbox, `/menu` присылает носитель заново.
- [Пользователь сам удалил носитель — клавиатура пропала] → `/start` или
  `/menu` присылает новый.
- [Носитель старше 48 часов остаётся в истории] → принятое ограничение;
  после появления кнопки `/menu` набирают редко, замены редки.
- [Текст «🏠 Меню» нельзя завести как задачу] → ничтожный риск, точное
  совпадение с эмодзи.
- [`/start` и `/menu` отправляют два сообщения подряд, а лимит outbox — одно
  сообщение в секунду на чат: меню приходит примерно на секунду позже] →
  принимается; кнопка «🏠 Меню» носитель не шлёт и задержки не даёт.
- [Каждый `/start` и `/menu` добавляет строку outbox и сообщение в чате —
  существующие тесты с точными проверками outbox и сообщений меняются] →
  отдельная задача на их обновление.

## Migration Plan

- Миграция добавляет nullable-колонку, откат — `DROP COLUMN`. Значение enum
  `keyboard` при откате остаётся: удалить значение enum Postgres не умеет.
  Строки outbox вида `keyboard`, не доставленные к откату кода, старый код не
  разберёт, и они уйдут в dead-letter — клавиатура придёт со следующим
  `/start` или `/menu` после повторного выката.
- Уже зарегистрированные пользователи получают клавиатуру при первом `/start`
  или `/menu` после выката.
- Откат кода без отката миграции безопасен: колонка просто не читается,
  клавиатура у пользователей остаётся, а нажатие кнопки до отката обработается
  как обычный текст по активному экрану.
