# Spec Delta

## ADDED Requirements

### Requirement: Режим размещения и единственность household

Система SHALL поддерживать режим размещения `single` (по умолчанию) и `multi`.
В `single` на инсталляции MUST быть не более одного активного household: ни
бот, ни CLI MUST NOT создавать второе. Проверка MUST быть единой для всех путей
создания и MUST оставаться верной при одновременных запросах. Удалённый household
не считается активным. В `multi` создание household ведёт себя как без этого
требования.

#### Scenario: CLI не создаёт второе пространство

- **WHEN** в режиме `single` уже есть активный household и администратор
  выполняет `tasklerq admin household create`
- **THEN** команда завершается ошибкой `409`
- **AND** новый household не создаётся

#### Scenario: Одновременный первый контакт

- **WHEN** на пустой инсталляции в режиме `single` два пользователя одновременно
  завершают онбординг
- **THEN** создаётся ровно один household
- **AND** второй пользователь получает сообщение, что пространство уже создано,
  и предложение попросить приглашение

#### Scenario: Пространство появилось во время онбординга

- **WHEN** пользователь начал онбординг на пустой инсталляции, а до его
  подтверждения household создали через CLI
- **THEN** подтверждение не создаёт второй household
- **AND** бот показывает экран, соответствующий новому состоянию инсталляции

#### Scenario: После удаления household

- **WHEN** в режиме `single` единственный household удалён
- **THEN** инсталляция считается пустой
- **AND** следующий допустимый пользователь может пройти онбординг

#### Scenario: Режим multi

- **WHEN** сервис запущен с `TENANCY_MODE=multi` и неизвестный пользователь
  отправляет `/start` без приглашения
- **THEN** бот запускает онбординг и создаёт для него новый household, как
  раньше

### Requirement: Деградация при нескольких household

Если в режиме `single` активных household больше одного, система SHALL
продолжать работу в деградированном режиме. При старте MUST записываться
ошибка в лог. Существующие пользователи MUST работать со своими household как
раньше. Создание household MUST быть запрещено. Неизвестный пользователь без
приглашения MUST получать сообщение о том, что требуется вмешательство
администратора.

#### Scenario: Старт с двумя household

- **WHEN** сервис в режиме `single` стартует, а в базе два активных household
- **THEN** сервис запускается
- **AND** лог содержит ошибку с количеством household без их названий
- **AND** HTTP API и бот продолжают обслуживать существующих пользователей

#### Scenario: Новый пользователь в деградированном режиме

- **WHEN** в деградированном режиме неизвестный пользователь отправляет `/start`
  без приглашения
- **THEN** бот сообщает, что инсталляция требует вмешательства администратора
- **AND** household не создаётся

#### Scenario: Приглашение в деградированном режиме

- **WHEN** в деградированном режиме пользователь открывает действительное
  приглашение
- **THEN** он присоединяется к household приглашения

## MODIFIED Requirements

### Requirement: Первый запуск и создание household

Система SHALL при первом обращении пользователя без приглашения учитывать
состояние инсталляции. В режиме `single` онбординг (запрос названия household и
часового пояса) MUST запускаться только на пустой инсталляции. Если задан
`BOOTSTRAP_OWNER_TELEGRAM_ID`, онбординг MUST быть доступен только этому
Telegram ID. Если household уже есть, система MUST NOT создавать новый:

- при наличии владельца пользователь получает предложение попросить приглашение;
- если владельца нет, бот показывает CLI-команду добавления владельца с
  подставленным Telegram ID пользователя и MUST NOT назначать владельца сам.

После подтверждения онбординга система MUST создать household, пользователя с
ролью `owner`, список задач «Задачи» и список покупок «Покупки». Состояние
инсталляции MUST повторно проверяться при подтверждении. Создание MUST быть
идемпотентным: повторная отправка того же шага не создаёт второй household.
Часовой пояс MUST быть валидным идентификатором IANA; по умолчанию предлагается
`Europe/Moscow`.

#### Scenario: Создание household

- **WHEN** новый пользователь отправляет `/start` без приглашения на пустой
  инсталляции
- **THEN** бот запрашивает название и часовой пояс
- **AND** после подтверждения создаёт household, владельца и два списка

#### Scenario: Пространство уже есть

- **WHEN** в режиме `single` неизвестный пользователь отправляет `/start` без
  приглашения, а у существующего household есть владелец
- **THEN** бот сообщает, что это частное пространство, и предлагает попросить
  приглашение у владельца
- **AND** household не создаётся

#### Scenario: Household без владельца

- **WHEN** в режиме `single` пользователь с Telegram ID `123456789` отправляет
  `/start` без приглашения, а единственный household не имеет владельца
- **THEN** бот показывает команду
  `tasklerq admin user add --telegram-id 123456789 --role owner`
- **AND** не назначает пользователя владельцем и не создаёт household

#### Scenario: Ограничение первого владельца

- **WHEN** задан `BOOTSTRAP_OWNER_TELEGRAM_ID=111` и пользователь с Telegram ID
  `222` отправляет `/start` на пустой инсталляции
- **THEN** бот сообщает, что пространство ещё не настроено, и предлагает
  обратиться к администратору
- **AND** не раскрывает ожидаемый Telegram ID
- **AND** household не создаётся

#### Scenario: Первый владелец из конфигурации

- **WHEN** задан `BOOTSTRAP_OWNER_TELEGRAM_ID=111` и пользователь с Telegram ID
  `111` отправляет `/start` на пустой инсталляции
- **THEN** бот запускает онбординг
- **AND** после подтверждения пользователь становится владельцем

#### Scenario: Владелец, добавленный администратором

- **WHEN** администратор выполняет
  `tasklerq admin user add --telegram-id <id> --role owner` для household без
  владельца
- **THEN** пользователь создаётся с ролью `owner`, а его чат совпадает с
  Telegram ID
- **AND** при первом обращении к боту он видит главное меню без онбординга

#### Scenario: Второй владелец через CLI

- **WHEN** администратор добавляет `--role owner` в household, где владелец уже есть
- **THEN** команда завершается ошибкой `409`
- **AND** владение передаётся штатным способом

#### Scenario: Некорректный часовой пояс

- **WHEN** пользователь вводит несуществующий часовой пояс
- **THEN** бот показывает список допустимых вариантов
- **AND** household не создаётся до исправления

#### Scenario: Повторный шаг онбординга

- **WHEN** пользователь повторно отправляет подтверждение создания household
- **THEN** система возвращает существующий household
- **AND** второй household не создаётся
