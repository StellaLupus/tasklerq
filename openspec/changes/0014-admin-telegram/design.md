# Design

## Context

Опирается на 0013: `settings` с шифрованием, учётка администратора, одноразовые
коды (`admin_one_time_codes` с `household_id`), снимок LLM, `http::client` с
доверенными сетями, `DomainTicker` (переход событий уже вне Telegram).
Текущее устройство Telegram:

- `telegram::runtime::start_with_update_limit` вызывается один раз из
  `build_application`, создаёт `HttpTelegramApi`, при webhook вызывает
  `setWebhook` и возвращает `Ingress`, который кладётся в `AppState` до сборки
  роутера. Воркеры (`UpdateWorker`, `CaptureWorker`, `Scheduler`,
  `OutboxWorker`, при polling — `poll`) получают общий процессный `shutdown`.
- `webhook::receive` при `state.telegram == None` отвечает `404`.
- `OutboxWorker::deliver_one` держит строку `FOR UPDATE SKIP LOCKED` в
  транзакции на время вызова Bot API и записывает `message_id` после ответа.
  `dedupe_key` защищает только от повторной постановки в очередь, а не от
  повторной отправки. Задания разбора возвращаются в очередь по истечении аренды
  `LEASE = 60 с`.
- `TELEGRAM_MODE` по умолчанию `webhook` и требует токен, секрет и
  `TELEGRAM_WEBHOOK_URL`; `TELEGRAM_BOT_USERNAME` по умолчанию `tasklerqbot`;
  `.env.example` задаёт `TELEGRAM_MODE=disabled`.
- `/start <аргумент>` обрабатывает `onboarding::on_start`: аргумент без префикса
  — код приглашения (16 символов, `random_base64url(12)`); если отправитель уже
  участник, аргумент игнорируется с баннером.
- `first_contact::classify(mode, bootstrap_owner, sender, installation)` —
  чистая функция; в `multi` сразу `Onboard`; `Single { has_owner: false }` с
  `bootstrap == sender` или без bootstrap → `AdminCommand`, с чужим bootstrap →
  `NotConfigured`.
- У сообщений исходящей очереди есть `delete_after`.

## Goals / Non-Goals

**Goals:**

- Подключить и переключить бота из консоли без перезапуска и без потери
  заданий.
- Закрыть окно «первый написавший — владелец» для инсталляций с консолью в
  `single`, не ломая `BOOTSTRAP_OWNER_TELEGRAM_ID` и онбординг в `multi`.
- Восстановление доступа к консоли из Telegram без превращения привязанного
  аккаунта в участника.

**Non-Goals:**

- Вход в консоль через Telegram — только восстановление пароля.
- Несколько ботов одновременно.
- Перенос `TENANCY_MODE` и параметров очередей в консоль.

## Decisions

### 1. Группа Telegram целиком из одного источника

Ключи `telegram.mode`, `telegram.bot_token` (секрет), `telegram.bot_id`,
`telegram.bot_username`, `telegram.public_base_url`,
`telegram.webhook_url_override`, `telegram.webhook_secret` (секрет). Если в
окружении задан `TELEGRAM_BOT_TOKEN`, вся группа берётся из окружения с прежней
валидацией. Иначе — из `settings`, а без строк Telegram выключен.

`TELEGRAM_MODE` без токена: `disabled` игнорируется с предупреждением (это
значение из прежнего `.env.example`, и оно не должно запирать консоль);
`webhook` и `polling` без токена — ошибка запуска, как сейчас. Одиночные
`TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_URL`, `TELEGRAM_WEBHOOK_SECRET` без
токена игнорируются с предупреждением. Почему ключ — именно токен: без токена
окружение не описывает бота целиком, а смешивание источников запрещено по той
же причине, что у слотов LLM (0013, решение 7).

Адрес webhook: `webhook_url_override` → `TELEGRAM_WEBHOOK_URL` (только вместе с
токеном из окружения) → `public_base_url + /webhooks/telegram`, где
`public_base_url` — из `PUBLIC_BASE_URL` или настройки. Адрес консоли не
годится: консоль в LAN, а Telegram ходит из интернета.

Нерасшифрованный токен или секрет webhook делает группу Telegram ненастроенной
целиком (0013, решение 8): бот выключен, readiness предупреждает.

### 2. Супервизор поколений

`TelegramSupervisor` владеет текущим поколением: `HttpTelegramApi`, набором
задач и собственным `watch`-каналом остановки, который также срабатывает от
процессного shutdown. `Ingress` переезжает в `ArcSwapOption<Ingress>` внутри
`AppState`.

Переключение (по сигналу из консоли после записи настроек):

1. `ingress.store(None)` и признак «идёт переключение»: webhook отвечает `503`
   с `Retry-After`, Telegram повторит доставку. В выключенном режиме (поколения
   нет и не будет) ответ остаётся `404`.
2. Кооперативная остановка: воркеры проверяют сигнал между итерациями.
   `OutboxWorker` не прерывает начатый `deliver_one` — вызов Bot API
   ограничен таймаутом клиента, после ответа записывается `message_id` и
   фиксируется транзакция. Поэтому на штатном пути сообщение не уходит дважды.
   Супервизор ждёт завершения до 30 секунд.
3. Если поколение не остановилось, супервизор логирует ошибку и делает `abort`.
   Это аварийный путь: прерванная посреди вызова отправка может повториться в
   новом поколении — для одного сообщения это допустимо и описано в рисках.
   Прерванное задание разбора вернётся в очередь по истечении аренды (60 с).
4. Новое поколение: `getMe`, `setWebhook` (или `deleteWebhook` + `poll`), новый
   `Ingress` → `store`.

Переключения сериализуются мьютексом супервизора. `CaptureWorker` читает снимок
LLM из 0013, поэтому смена слотов поколение не пересоздаёт. Переход событий уже
вынесен в `DomainTicker` (0013, решение 11); в поколении остаются отмена
устаревших доставок и планирование напоминаний и сводок — без бота им некуда
доставлять, а пауза на секунды не нарушает гарантий: доставки досылаются по
времени из базы.

Polling: висящий `getUpdates` прежнего поколения отменяется вместе с задачей;
если Telegram всё же ответит новому поколению `409 Conflict`, `poll` повторяет
запрос с задержкой, а не завершается.

Альтернатива — перезапуск процесса: отвергнута, как в 0013. Альтернатива —
подменять токен в живом `HttpTelegramApi`: не покрывает смену режима и секрета
`Ingress`.

### 3. Подключение и смена бота

Консоль сначала вызывает `getMe` с введённым токеном отдельным клиентом, не
трогая поколение. Если id бота совпадает с сохранённым или участников нет —
сохранение сразу. Если id другой и в `users` есть активные участники — форма
подтверждения с предупреждением. После переключения — best-effort
`deleteWebhook` прежним токеном, чтобы старый бот не слал обновления с
устаревшим секретом и не раздувал счётчик отказов webhook.

Секрет webhook генерируется `random_base64url(32)` при первом сохранении и по
кнопке «перевыпустить»; пользователь его не вводит.

### 4. Разбор `/start` с префиксами

`on_start` сначала проверяет префиксы `own_` и `adm_` — до ветки «уже
участник», иначе привязка администратора, который сам участник, была бы
невозможна. Префикс распознаётся вместе с длиной кода (22 символа base64url);
код приглашения — 16 символов без префикса, поэтому пересечения нет.
Недействительный код с префиксом ведёт себя как `/start` без аргумента.

Назначения одноразовых кодов: `owner_claim` (24 часа, `household_id` — дом
или NULL для пустой инсталляции в `single`; CHECK: NULL допустим только для
этого назначения) и `telegram_link` (15 минут). Гашение прежних кодов идёт по
паре `(purpose, household_id)`, поэтому в `multi` ссылка дома B не гасит
ссылку дома A.

Claim household без владельца: код расходуется атомарным
`UPDATE ... RETURNING` в одной транзакции с созданием владельца — одновременный
claim даёт ровно одного владельца. Claim пустой инсталляции: на `/start`
действительность кода только проверяется, а код (его id) сохраняется в
состоянии диалога онбординга; расходуется он в транзакции создания household.
Если код истёк или израсходован к моменту подтверждения, онбординг
завершается экраном, соответствующим текущему состоянию (как при гонке с CLI
сейчас).

### 5. Классификатор первого контакта

`classify` получает входы `claim: Option<ClaimTarget>` (код действителен; цель
— пустая инсталляция или household без владельца) и `admin_exists: bool`.

| Режим | Состояние | claim | bootstrap | admin_exists | Исход |
| --- | --- | --- | --- | --- | --- |
| multi | любое | есть, для дома без владельца | — | — | ClaimOwner |
| multi | любое | нет | — | — | Onboard (как раньше) |
| single | Empty | есть | — | — | Onboard |
| single | Empty | нет | = отправитель | — | Onboard |
| single | Empty | нет | ≠ отправитель | — | NotConfigured |
| single | Empty | нет | нет | нет | Onboard (как раньше) |
| single | Empty | нет | нет | да | NotConfigured |
| single | без владельца | есть | — | — | ClaimOwner |
| single | без владельца | нет | = отправитель | — | ClaimOwner |
| single | без владельца | нет | ≠ отправитель | — | NotConfigured (как раньше) |
| single | без владельца | нет | нет | — | AdminCommand (с подсказкой о ссылке при admin_exists) |
| single | с владельцем / Multiple | — | — | — | как раньше |

Строка «без владельца + bootstrap = отправитель → владелец» нужна, потому что
мастер 0013 может создать household без владельца при Telegram из окружения:
без неё `BOOTSTRAP_OWNER_TELEGRAM_ID` после мастера вёл бы к CLI-команде.
Функция остаётся чистой и покрывается табличным тестом; существующий тест
`household_without_owner_shows_the_admin_command` остаётся верным для строки
«bootstrap нет».

### 6. Привязка и восстановление

`admin_accounts.telegram_user_id` (NULL, уникальный) и
`admin_accounts.pending_telegram_user_id` с именем аккаунта. `/start adm_…`
записывает кандидата; консоль показывает его имя и кнопки «подтвердить /
отклонить». Подтверждение переносит кандидата в `telegram_user_id`, бот
сообщает о привязке. Ссылка предъявительская — подтверждение в консоли не даёт
постороннему, открывшему ссылку первым, получить канал восстановления.

`/admin` проверяет отправителя по `telegram_user_id`; для остальных — ответ как
на неизвестную команду. Ссылка восстановления — код назначения `recovery` из
0013 на `admin_accounts.console_origin`, который обновляется при каждом
успешном входе по origin запроса (с учётом `ADMIN_TRUSTED_PROXIES`). Без адреса
— подсказка про CLI. Сообщение уходит через outbox с `delete_after = 15 мин` и
отключённым предпросмотром ссылки. Лимит — новый ключ `rate_limit` (3 в час на
аккаунт).

Новые значения `audit_event_type`: `admin_telegram_linked`,
`admin_telegram_unlinked`; выпуск ссылки — существующее
`admin_recovery_issued`; назначение владельца по claim — существующее событие
членства `member_joined` с источником «claim».

### 7. QR-код

SVG генерируется на сервере (`qrcode` с рендером SVG) и вставляется инлайн —
ссылка-claim не уходит третьей стороне.

## Risks / Trade-offs

- [Во время переключения webhook отвечает `503`] → Telegram повторяет доставку;
  переключение — секунды.
- [Аварийный `abort` посреди отправки] → возможен один повтор сообщения; путь
  только при зависшем поколении дольше 30 секунд, логируется как ошибка.
- [Смена бота отрезает участников до их `/start`] → явное подтверждение с
  числом участников; документация описывает, что сказать семье.
- [Ссылка-claim переслана постороннему] → 24 часа, одноразовая, гаснет при
  выпуске новой; консоль показывает, кто стал владельцем.
- [Компрометация привязанного Telegram-аккаунта] → ссылка ведёт на адрес
  консоли, обычно доступный только из LAN, действует 15 минут, выпуск в аудите.

## Migration Plan

1. Миграция аддитивна: `admin_accounts.telegram_user_id`,
   `pending_telegram_user_id`, `console_origin`, новые назначения и CHECK у
   `admin_one_time_codes`, новые значения `audit_event_type`.
2. Инсталляции с `TELEGRAM_BOT_TOKEN` в окружении работают как раньше. Строка
   `TELEGRAM_MODE=disabled` без токена теперь игнорируется с предупреждением.
3. Перенос бота в консоль: ввести токен в консоли, удалить `TELEGRAM_*` из
   `.env`, пересоздать контейнер (одно пересоздание нужно, чтобы окружение
   перестало перекрывать базу).
4. Откат на 0013-образ: настройки Telegram из базы старый образ не читает —
   вернуть `TELEGRAM_*` в `.env` перед откатом.
