# Design

## Решения

### 1. Стандарт — настройка слота в базе

Режим сравнения названий — не флаг печати и не свойство отчёта, а стандарт
проверки слота. Его хранит `llm_slot_settings` (`slot` — ключ, `titles`,
`updated_at`): одна строка на слот, как у `llm_slot_checks`. Отсутствие строки
означает `strict`, поэтому миграция не пишет данных и прежнее поведение
сохраняется.

Почему база, а не окружение: env описывает подключение к слоту, а стандарт
проверки — решение оператора, которое должно переживать перезапуск и меняться
командой проверки. Почему не `report jsonb`: стандарт нужен статусу и readiness
до чтения проверки и должен проверяться ограничением, а не жить внутри отчёта.

Почему не household: `llm_slot_checks` — строка на слот, слот задан в env, а
smoke-набор фиксирован; при `TENANCY_MODE=multi` нет одного household, чей
стандарт описывал бы статус слота. Гранулярность совпадает с проверкой; когда
появятся per-household модели и per-household проверки, настройка переедет
вместе с ними.

### 2. Стандарт в отпечатке — и почему это не тавтология

`FingerprintParts` получает седьмое поле `titles`. Действующий отпечаток
считается по стандарту **из настроек**, а не из сохранённой проверки: иначе
сравнение стало бы сравнением значения с самим собой. Поэтому смена стандарта
даёт другой отпечаток и статус «устарел» — как смена модели.

### 3. Сохранённый стандарт — в частях отпечатка

Отдельная колонка `llm_slot_checks.titles` не нужна: `fingerprint_parts` уже
хранится jsonb и после решения 2 содержит `titles`. `latest` читает
`coalesce(fingerprint_parts->>'titles','strict')`; старая строка без поля —
строгая, чем она и была. Дублировать значение в колонке значило бы держать три
копии одного режима (настройка, части отпечатка, отчёт) и следить за их
согласием.

### 4. `--titles` задаёт стандарт, значения по умолчанию нет

Флаг сохраняет выбранный режим за слотом и судит прогон по нему. Без флага
берётся сохранённый стандарт; жёсткий `default_value = "strict"` у CLI убран —
иначе обычный прогон без флага молча сбрасывал бы нормализованный стандарт.

Запись настройки и записи проверки идут одной транзакцией: иначе смена
стандарта без новой проверки оставила бы слот «устарел» без объяснения, а
проверка со старым стандартом могла бы выглядеть свежей.

### 5. Статус и видимость стандарта

`slot_status::status` принимает действующий стандарт, `SlotStatusReport`
называет стандарт сохранённой проверки (`None` — проверки нет). Строка лога
старта и предупреждение readiness дополняются режимом, когда проверка есть:
`llm_slot_unverified:<slot>:<режим>`. Статус по-прежнему не блокирует работу.

### 6. Один прогон — два судейства

`collect_runs` и `evaluate_with` уже разделены: вызовы слота платные и
недетерминированные, оба режима судят один набор исходов. Отчёт печатает число
пройденного для действующего стандарта всегда, для второго режима — когда
судейство удалось. Ошибка второго судейства не должна скрывать первое число.

### 7. Границы нормализации

Нормализация сближает названия **элементов**: основы слов, инфинитивные
видовые пары и синонимы. Имена списков остаются строгими: список — идентификатор
из контекста household, и боевая валидация (`context::find_list`) требует
точного имени. Нормализация там позволила бы принять один существующий список
за другой, если оба имени попали в словарь синонимов.

Подбор пар элементов остаётся режимным намеренно: паросочетание биективно,
лишние и недостающие элементы всё равно попадают в отчёт, а совпавшая пара
дополнительно сравнивается по полям. Строгий подбор дал бы «недостающий +
лишний» вместо настоящего расхождения полей — меньше информации.

### 8. Словарь видовых пар — явный список по наблюдениям

Словарь остаётся явным: пара добавляется, когда в прогонах видно расхождение по
виду глагола. Добавляем «заплатить → платить» — единственный провал, где
разница только в названии. Автоматическое отсечение приставок не годится: оно
склеило бы разные глаголы («писать» и «описать», «переписать») и превратило бы
нормализацию в угадывание. По той же причине словарь остаётся коротким:
непокрытая пара — видимое расхождение, а не ложное совпадение.

## Миграция

`0019_llm_slot_settings.sql`:

```sql
CREATE TABLE llm_slot_settings (
    slot text PRIMARY KEY CHECK (btrim(slot) <> ''),
    titles text NOT NULL DEFAULT 'strict'
        CHECK (titles IN ('strict', 'normalized')),
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

`llm_slot_checks` не меняется.

## Совместимость

- По умолчанию стандарт строгий: строки в `llm_slot_settings` нет — `strict`.
- Старая проверка не имеет `titles` в частях отпечатка и читается как строгая.
- Седьмая часть меняет отпечаток, поэтому после обновления каждая сохранённая
  проверка один раз становится «устарел»; статус возвращается повторным
  `capture-eval` по слоту. Шаг записан в чек-лист обновления.

## Проверка

- Юнит: смена стандарта меняет отпечаток, смена токена — нет; видовые пары
  (включая «заплатить/платить») и синонимы; имена списков не нормализуются;
  `evaluate_with` — один прогон, два вердикта.
- Интеграционные: CLI с видовой парой — оба числа, код возврата по стандарту,
  стандарт записан в `llm_slot_settings`, режим в частях отпечатка; прогон без
  флага берёт сохранённый стандарт; смена стандарта делает проверку устаревшей;
  миграция на базе со старой проверкой.
