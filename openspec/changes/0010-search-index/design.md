# Design

## Context

Мотивация — в proposal.md (Why). Текущее состояние поиска
(`src/storage/repositories/items/find.rs`, функция `search`):

- Один статический SQL. Все фильтры записаны как `($N IS NULL OR …)`, текстовое
  условие `$9` — это `OR` из пяти веток: `search_vector @@ plainto_tsquery`,
  `strpos(lower(title), lower($9)) > 0`, то же по `notes`, `EXISTS` по тегам и
  `EXISTS` по подзадачам.
- Индексы: GIN по `items.search_vector`, GIN `gin_trgm_ops` по `items.title`
  (`items_title_trgm_idx`, создаётся только при доступном `pg_trgm`),
  `tags (household_id, lower(name))`, `item_tags (tag_id)`,
  `subtasks (item_id, position)`.
- `strpos(lower(...))` не может использовать trigram-индекс, а `OR` с
  коррелированными `EXISTS` не даёт планировщику собрать `BitmapOr`. Поэтому
  каждый поиск — полный проход по задачам household с подзапросами на строку.
- Ранжирование: `ts_rank(search_vector, plainto_tsquery(...))` плюс `1.0`, если
  подстрока есть в названии. Порядок: `rank DESC, sort_due ASC, id ASC`.
  Курсор — тройка `(rank, due, id)`.
- `tests/search.rs` покрывает совпадения по всем четырём полям, фильтры,
  стабильность курсора и `search_treats_sql_and_like_syntax_as_plain_text`
  (символы SQL и `LIKE` ищутся буквально).

В нагрузке `make load` поиск с запросом «Купить молоко» или «Позвонить маме»
идёт по household из 10 000 задач, и число задач с этими названиями растёт по
ходу прогона, потому что те же тексты на других экранах создают задачи.

## Goals / Non-Goals

**Goals:**

- При доступном `pg_trgm` поиск с непустым запросом из трёх и более символов
  отбирает кандидатов по индексам, а не полным проходом по household.
- Набор результатов, порядок, курсор и фильтры совпадают с текущими для любого
  запроса. `tests/search.rs` проходит без изменения ожиданий.
- `make load` проходит без изменения профиля и критериев.

**Non-Goals:**

- Менять маршрутизацию текста на экране поиска (`9a6557c`): новый запрос с
  экрана результатов — нужное поведение.
- Выносить поиск из воркера обновлений, кешировать результаты, ограничивать
  частоту поиска.
- Ускорять запросы короче трёх символов: trigram-индекс для них бесполезен,
  они идут прежним планом.
- Менять ранжирование (`ts_rank`, бонус за название) и полнотекстовую
  конфигурацию `simple`.

## Decisions

### 1. Подстрока через `ILIKE` с экранированием, а не `strpos(lower(...))`

`gin_trgm_ops` поддерживает `LIKE`/`ILIKE` с шаблоном `%…%`, а `strpos` — нет.
Шаблон строится в Rust: в запросе экранируются `\`, `%`, `_` (в этом порядке),
затем он оборачивается в `%…%`; в SQL — `ILIKE $p` (escape-символ по умолчанию
`\`). Так сохраняется поведение
`search_treats_sql_and_like_syntax_as_plain_text`.

Альтернативы:
- индекс по выражению `lower(title) gin_trgm_ops` и `lower(title) LIKE
  lower($p)` — даёт то же, но требует пересоздать существующий индекс по
  `title`; `ILIKE` работает с имеющимся;
- `pg_trgm` операторы схожести (`%`, `<%`) — меняют семантику с «есть
  подстрока» на «похоже», это изменение поведения.

Бонус ранжирования за название остаётся тем же выражением
(`strpos(lower(title), lower($q)) > 0`): он вычисляется только для отобранных
кандидатов, на план не влияет, а сравнение регистра остаётся прежним.

### 2. Кандидаты отбираются объединением, а не `OR` с `EXISTS`

При непустом запросе id кандидатов собираются в CTE через `UNION`:

- задачи household с `title ILIKE $p OR notes ILIKE $p OR search_vector @@
  plainto_tsquery('simple', $q)` — все три ветки по индексам одной таблицы,
  планировщик собирает `BitmapOr`;
- `subtasks.item_id`, где `title ILIKE $p` (новый trigram-индекс);
- `item_tags.item_id` по тегам household, где `name ILIKE $p` (тегов в
  household мало, проход по ним дешёвый, дальше `item_tags_tag_idx`).

Основной запрос соединяет `items` с кандидатами и применяет прежние фильтры,
ранжирование, курсор и `LIMIT`. Удалённые задачи и архивные списки
отсекаются в основном запросе, как сейчас.

Альтернатива — оставить один `WHERE` и заменить только `strpos` на `ILIKE`:
`OR` с коррелированными `EXISTS` всё равно оставляет проход по всем задачам
household, выигрыш только на стоимости сравнения строк.

### 3. Два текста SQL: с текстовым запросом и без

Условие вида `($9 IS NULL OR id IN (кандидаты))` в подготовленном запросе
планируется общим планом и не даёт отбросить ветку. Поэтому `search` выбирает
один из двух SQL в Rust: с CTE кандидатов (запрос непустой) и без него
(только фильтры, как сейчас). Остальные фильтры остаются в форме
`($N IS NULL OR …)`: они по индексированным колонкам household и в проблему не
входят.

### 4. Миграция `0015_search_trgm.sql` — только индексы, условно

По образцу `0002`: если расширение `pg_trgm` есть, создаются
`items_notes_trgm_idx ON items USING gin (notes gin_trgm_ops)` и
`subtasks_title_trgm_idx ON subtasks USING gin (title gin_trgm_ops)`
(`IF NOT EXISTS`). Расширение миграция не создаёт: это уже делает `0002`, а
повторная попытка у роли без прав только шумит. Без `pg_trgm` миграция ничего
не меняет, поиск работает прежним полным проходом.

Без `CONCURRENTLY`: миграции идут в транзакции, а объём household мал —
построение индекса занимает секунды при старте.

## Risks / Trade-offs

- [`ILIKE` и `lower()` по-разному сворачивают регистр] → оба используют
  `LC_CTYPE` базы. Отбор кандидатов идёт по `ILIKE`, бонус ранжирования — по
  `lower()`. Расхождение возможно только для экзотических символов и влияет
  только на бонус. Кириллица и латиница покрыты тестами `tests/search.rs` с
  разным регистром.
- [Запрос короче трёх символов не использует trigram-индекс] → такие запросы
  идут прежним полным проходом. В `make load` запросы длинные. Отдельно не
  оптимизируется (Non-Goals).
- [Число совпадений растёт по ходу нагрузки: тексты создают задачи с теми же
  названиями] → после отбора по индексу ранжируются только совпадения, а их
  сотни, а не 10 000. Если `make load` останется красным, первым делом — `EXPLAIN
  (ANALYZE, BUFFERS)` поиска на данных нагрузки: что занимает время после
  отбора.
- [Планировщик выберет полный проход на маленьких тестовых базах] → тесты
  проверяют результаты, а не план. План проверяется на данных нагрузки
  (10 000 задач) и записывается в `docs/deployment.md` §20.
- [Два текста SQL расходятся при будущих правках] → общие части (список
  колонок, фильтры, ранжирование, порядок, курсор) собираются из одних
  констант, различается только источник строк.

## Migration Plan

1. Миграция `0015` применяется при старте, как остальные. Индексы на `items`
   и `subtasks` строятся за секунды на объёме household.
2. Откат кода — предыдущий образ: старый SQL работает и с новыми индексами
   (они просто не используются). Миграции в проекте только прямые; индексы
   при откате можно оставить или удалить вручную `DROP INDEX`.
3. На NAS расширение `pg_trgm 1.6` уже установлено, индексы создадутся.
