# Design

## Context

Рефакторинг и тесты, мотивация — в proposal.md. Внешнее поведение не
меняется. Страховка — существующий набор тестов: он должен проходить, а
ожидания меняются только там, где удаляется `has_next`.

Change идёт после 0007: тот правит сборку баннера в `capture_worker.rs`
и `shopping.rs`. Если сделать рефакторинг раньше, будут конфликты.

## Goals / Non-Goals

**Goals:**

- Убрать копии, которые меняются вместе.
- Закрыть пробелы в тестах и флак.

**Non-Goals.** Пункты из PR, которые при проверке оказались не долгом:

- **Один разбор JSON обновления (PR 6).** Вредно. `Update` из `teloxide-core`
  использует `#[serde(flatten)]`, и `from_value` молча теряет поля сообщения
  (`src/telegram/update.rs:134-141`). Боли от двойного разбора нет.
- **Тест `in_step` (TODO в `bot/mod.rs:787`).** Прямые тесты уже есть в
  `tests/telegram_steps.rs`. TODO говорит о сквозном тесте для первого
  действия, которое пишет до `Fail::User`. Такого действия пока нет.
- **Одна проверка версии в `card::reopen` (PR 19).** Вредно. На пути возврата
  выполнения сверка в `card.rs:738` единственная: `revert_completion`
  версию не принимает.
- **`revert_completion` отклоняет покупки (PR 19).** Единственный вызов уже
  защищён веткой в `card.rs`.
- **Разбиение `editor.rs` и конструктор `Editor` (PR 16).** Файл связный, это
  один автомат редактора, и правок в нём не запланировано: боли нет. Литералы `Editor { … }` лежат в
  `forms/mod.rs` и `bot/capture/mod.rs`, и общего в них — шесть константных
  полей. Выбор списка по умолчанию — это три разных правила
  (`forms/mod.rs:137`, `:217`, `bot/capture/mod.rs:825`), а не дубль.
- **Явный режим размещения в конструкторах (PR 8).** Оба боевых вызова уже
  передают режим явно (`app.rs:73`, `telegram/runtime.rs:107`). Тестовый
  стенд `harness_bot` намеренно ставит `Multi`.
- **Общий `PAGE_SIZE` (PR 19).** Значение совпадает, но константы лежат в
  разных слоях. Общая константа требует импорта из `telegram` в `storage`.
- **Вывод текста из `SECRET_MESSAGE_TTL`, спойлер через `rich.rs`, перенос
  `names`/`parent_list_name` (PR 8, 19).** По одному потребителю, это
  эстетика.
- **Функция «fallback или 503» и слияние `responder`/`reservation` (PR 2).**
  Общая часть уже вынесена в `apply_fallback`. Остатки веток различаются
  текстом и кодом ответа, а `responder` всегда `Some`.
- **Хелперы вставки и чтения snooze (PR 20).** SQL и сигнатуры разные, это
  не копии.
- **Замер предельной ёмкости воркера (PR 6).** Семейная нагрузка на порядки
  ниже 50 обновлений в секунду, а цифра с машины разработчика ничего не
  говорит о NAS.
- **Циклическая зависимость модулей доставки, общий каркас конвейеров,
  `menu_counts` (PR 5, 14).** Абстракция без второго потребителя или
  оптимизация без замера.

## Decisions

### 1. Общая функция добавления частей

Обе функции почти дословно делают одно и то же:
- сборку `new_items` из `split_titles`;
- цикл `plan_additions` / `merge_duplicate_choice` / `validate_new_item` с
  пропуском `Validation`;
- `items::create`.

Общее ядро уходит в функцию над `&mut PgConnection`. Она возвращает
`Result<Added, DomainError>`, где `Added` — созданные позиции, выборы
дубликатов и пропущенные части. Проверка `MAX_ITEMS`, поиск списка, перевод
ошибки (`into_sqlx` или `Fail`) и показ результата остаются у вызывающих.

### 2. Предел количества

`pub const MAX_INPUT_QUANTITY: f64 = 9_999.0` в `src/domain/validation.rs`,
рядом с доменной проверкой `9999.999`. Одна константа ввода нужна в двух
слоях (бот и capture), а домен — общий нижний слой. Доменный предел
`9999.999` остаётся отдельно: он шире, допускает дробную часть и защищает
хранение. Комментарий у констант объясняет разницу. Значения не меняются.

### 3. `expect` в `batch.rs`

В `jobs/batch.rs` около стр. 225 вид уже проверяется через
`DeliveryScope::of(row.kind)`. Там пишется `let Some(scope) = … else
{ continue };`, `scope` сохраняется в `BatchCandidate`, и `expect` около
стр. 337 исчезает.

### 4. Флак snooze

Расхождение возникает в стенде. `Harness::tick()`
(`tests/support/telegram.rs:435`) берёт `Utc::now()` при каждом `enqueue`,
а тест читает `bot.now` до нажатия. Тест берёт ожидание от `snoozed_at`
(или `created_at`) записи в базе плюс час. Можно и так: проверять, что время
попадает в интервал `[now до нажатия, now после] + 1 ч`. Боевой код не
меняется.

## Risks / Trade-offs

- [Общая функция добавления частей меняет порядок ошибок] → её покрывают
  существующие тесты прямого добавления (`tests/telegram_capture.rs`,
  `tests/capture_fallback.rs` и тесты экрана покупок) без изменения ожиданий.
- [Удаление `has_next` меняет тест] → в `tests/item_lifecycle.rs` его вызовы
  дублируют `assert_eq!(pages, 2)` и удаляются вместе с ним.
